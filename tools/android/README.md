# DSP for Android: sensors with the screen locked

A thin Android app around the DSP workbench. A browser tab is frozen as soon as the screen locks (sensors and timers stop),
so the app runs a **foreground service** that owns the hardware and serves it on a local port. The page connects to it and gets
sensors up to 200 Hz, GPS and everything the satellites say, Wi-Fi, Bluetooth LE / classic, battery.

- **App** (`MainActivity`): the whole workbench from `assets/www` in a WebView (works offline), asks for Notifications only; every other permission (Location, Microphone, Nearby devices, Physical activity) is requested when a page asks for the source that needs it — a window if the app is on screen, otherwise a notification to tap, starts the service. Blob downloads go to *Downloads*, file inputs open the system picker.
- **Service** (`BridgeService`): notification with *Settings* / *Stop*, partial wake lock while something is requested. Sources start only when a client subscribes.
- **Server** (`BridgeServer`, one port, default `127.0.0.1:8765`):
  - `ws://host:8765/?token=…` — the protocol of [`tools/termux/bridge.mjs`](../termux/bridge.mjs): send `{"sub":["accel","gyro","gps","wifi","battery",…],"hz":200}`, get JSON records (arrays of them, one batch per ~40 ms). Sensor records are `{src:'sensor', sensor, t, x, y, z}` with `t` in ms (the time of the measurement, not of the delivery). Sensors (only those the phone has; the `hello` message lists them): `accel gyro mag light pressure proximity gravity linear rotation` (`x y z w` — quaternion), `gamerot georot` (same, without the magnetometer / without the gyroscope), `accelraw gyroraw magraw` (uncalibrated: `x y z` + bias `bx by bz`), `ambtemp` (°C), `humidity` (%), `steps` (counter since boot; needs the Physical activity permission), `heading` (° and `acc`, Android 14+), `hinge` (° , foldables), `step` (detector), `devorient` (screen orientation 0–3, Android 13+), and the one-shot triggers `sigmotion`, `stationary`, `motion` (re-armed after each firing). The `hello` message carries `sensorInfo`: every sensor of the phone (name, vendor, range, resolution, `maxHz`, power, FIFO), also those the bridge does not map; `/status` lists them too. Other sources (each is subscribed separately; position-tagged ones carry `lat`, `lon`, `acc` of the last fix, not older than 30 s):
    - `gps` — `{src:'gps', lat, lon, alt, acc, speed, bearing, provider}`; `battery` — `{pct, status, plugged, temp}`.
    - `wifi` — a scan every `wifiEvery` s (`{"sub":["wifi"],"wifiEvery":10}`): `bssid, ssid, rssi, freq, ch, band, bw` (channel width, MHz), `cf0 / cf1` (centre frequencies), `caps` (WPA / RSN / WPS flags as Android shows them), `std` (n / ac / ax / be), `age` (ms since the scan), `hidden`, `mc` (802.11mc ranging), `pass` (Passpoint), `op` / `venue`; from the access point's information elements (Android 11+): `country`, `vendors` (OUIs), `wps`, `wpsMfr / wpsModel / wpsName`. Plus `{src:'wificonn'}` — the network the phone is connected to (rssi, link speed, tx / rx rate).
    - `ble` — one record per advertisement: `addr, name, rssi, txp, conn, flags, app, uuids[], mfr{companyId: hex}, svc{uuid: hex}, raw` (the advertisement bytes in hex) — parse further on the page. `bt` — classic Bluetooth discovery (rounds of about 12 s): `addr, name, rssi, cls, major`.
    - `cell` — a poll every `cellEvery` s (`{"sub":["cell"],"cellEvery":5}`): `type` (LTE / NR / GSM / WCDMA / CDMA), `reg` (1 — serving), `mcc mnc cid pci tac lac psc arfcn band bw`, `rsrp rsrq sinr cqi ta rssi dbm lvl`, plus the last position.
    - `mic` — PCM 16-bit mono in 20 ms chunks: `{src:'mic', t, sr, rms, peak (dBFS), pcm (base64, little-endian)}`, rate from `micHz` (8000–48000; the unprocessed input when the phone has one). Needs the service started while the app is on screen (Android rule), like the camera.
    - `pkt` — packet capture, **root only**: `su -c tcpdump -i <iface> -U -n -s <snap> -w - '<filter>'` (`{"sub":["pkt"],"iface":"wlan0","filter":"tcp port 80","snap":256}`), the pcap stream becomes `{src:'pkt', t, iface, link, len, cap, hex, smac, dmac, ethtype, ip, dip, proto, sport, dport}` (`hex` is the frame as captured, Ethernet / Linux-cooked / raw IP). Off until *Allow packet capture* is ticked in the app Settings; the interface and the filter are checked against a strict character set before they reach the root shell. Without root Android has no raw sockets for apps, and cellular modem frames are not reachable at all.
    - `gnss` — per satellite `{kind:'sat', con, svid, cn0, el, az, used, eph, alm, freq, band}` and a summary `{kind:'fix', n, used, cn0}`. `gnssraw` — raw measurements: `{kind:'clock', tn, bias, fullbias, drift, hw}` and `{kind:'meas', con, svid, cn0, prr, prrunc, adr, adrstate, tx, txunc, state, off, mp, freq, band}` (what GNSS Logger writes; many phones switch the duty cycling off only in *Developer options*). `nmea` — `{src:'nmea', line}` as the receiver prints them.
  - `http://host:8765/status` — text.
- **In the workbench:** the *Phone sensors (Termux / DSP app)* node — *sensor rate*, *Wi-Fi scan every*, *Bluetooth LE / classic*, *GNSS*, *GNSS raw*, *NMEA*. Outputs: `nmeatxt` (NMEA sentences → *NMEA Parser* `text`), `nsat`, `nused`, `cn0` (satellites in view / used / mean C/N0 of the used), `rec` for everything else. Presets *Phone App: Satellites, Bluetooth and Wi-Fi Scan*.

## USB

The WebView has no WebUSB, so the bridge has a **general USB API** and the workbench builds `navigator.usb` on it (`modules/usb-bridge.js`; it does nothing outside the app). RTL-SDR, HackRF, Airspy, RX888, logic analysers, USB serial adapters and the rest of the USB modules then work in the app as in Chrome. Plug a device with an OTG cable; the first `requestDevice` shows Android's permission dialog (and a small chooser when several devices match). Isochronous transfers are not available (`UsbDeviceConnection` has none); `reset` works where the phone allows it; workers have no `navigator.usb`, so the SDR code opens the dongle on the main thread.

- `ws://127.0.0.1:8765/usb?k=<key>` — **only from this phone and only with the key** that the app hands to its own page (`DspApp.usbUrl()`); other sites and apps do not know it, because this port reads and writes to attached devices. Binary messages `[u32 BE header length][header JSON][payload]`; request `{id, op, dev, …}`, answer `{id, ok:true, …}` or `{id, ok:false, err:<DOMException name>, msg}`, events `{ev:'connect'|'disconnect', …}`.
- Operations: `list` (devices with `perm`, descriptors: `vid pid cls sub proto ver mfr prod serial configs[{value, ifaces[{num, alt, cls, sub, proto, eps[{num, in, type, size}]}]}]`; names and serial number only after access), `perm` (the Android dialog), `open` (answers with `configs`, `usb`, `speed` parsed from the raw descriptors — the Android model of the device may hide alternate settings, e.g. Mirics alt 3; `speed` is `high-speed` / `full-speed` by the bulk packet size), `close`, `config {value}`, `claim {num}` (the kernel driver is detached), `release`, `alt {num, alt}` (a setting missing in the Android model is selected with SET_INTERFACE; its endpoints are built from the raw descriptors where the Android version allows), `control {rt, req, val, idx, len}` (+ payload for OUT), `in {ep, len}` (waits for data like WebUSB; up to 8 MB, a short packet ends it), `out {ep}` + payload, `clear {ep}`, `reset`.

## Commands: notifications, flashlight, SMS, contacts, IR

Besides subscriptions the socket takes **commands**: `{"cmd":"…","id":N,…}`; the answer is a record `{src:'cmd', cmd, id, ok, …}` to that client only (`err` is `permission` — asked in a window or a notification, repeat after allowing —, `forbidden`, `rate`, `unknown` or `error`, with `msg`). In the workbench the *Phone Actions* node does all of it.

- `notify {title, text, actions:[{id,label}≤3, open, ongoing, nid}]` — a native notification; a tap on it or on a button arrives as `{src:'notify', nid, action}` (`tap`, `dismiss` or the button id) for clients subscribed to `notify` (with `open:true` the tap opens the app and no event is sent: since Android 12 a receiver cannot start a window). `notify.cancel {nid}`.
- `torch {on, level}` — the flash as a flashlight (`level` — brightness, Android 13+); the state goes out as `{src:'torch', on}` to subscribers of `torch`.
- `ir.info` → `{has, ranges}`; `ir.send {freq, pattern:[µs…]}` — the phone's IR emitter (ConsumerIrManager; many phones have none, and Android has **no API for an IR receiver**, so frames can only be sent). The carrier must lie in the emitter ranges.
- **Personal data and money — only the page of the app** (it adds the app key, `?k=`, to the address; any other site or app is `forbidden` and cannot even subscribe to `sms`): `sms.send {to, text}` (answers when every part is sent; at most 5 a minute), `sms.data {to, hex, port}` — binary SMS to an application port (`SmsManager.sendDataMessage`), `sms.send_raw {pdu, smsc}` — a hand-built TPDU hex (no SMSC prefix — pair with the *SMS PDU* node's `tpdu` output; `smsc` optional, hex SMSC bytes) sent as-is; **best-effort**: Android's `SmsManager` has no public method for it, so the app reaches the internal `ISms.sendRawPdu` by reflection (`RawPdu.kt`, with `HiddenApi.kt`'s `VMRuntime.setHiddenApiExemptions` trick) — works on many phones (older Android, most custom ROMs), refused outright on others once the hidden-API denylist is enforced strictly; the error distinguishes "no such method" from other failures. `sms.list {box:all|inbox|sent, q, since, limit≤500}` and `contacts.find {q, limit≤500}` (the records come first — `{src:'sms', dir, addr, body, t, read, pdu, pdus, parts, sc}`, `{src:'contact', id, name, phones[]}` —, then the answer with `n`), subscription `sms` — incoming messages `{src:'sms', dir:'in', addr, body, t, pdu, pdus}` (`pdu` — the first part's raw hex TPDU, `pdus` — every part's, for a multipart message; feed straight into the *SMS PDU* node's `hex` input, which also takes an array). Permissions (SMS, contacts, notifications) are asked at the first use.
- `vibrate {ms, amp}` / `vibrate {pattern:[off,on,off,…], repeat, amp}` / `vibrate {effect:'click'|'double'|'heavy'|'tick'}` — the phone's vibrator; `amp` 1–255 on phones with amplitude control. `vibrate.stop`.
- `sys.bcast.listen {actions:[…]}` — registers a receiver for any list of intent actions (the app's own hardcoded set in the *System events* subscription below, or anything else: another app's custom broadcast, a less common system one); records `{src:'sys', ev:'broadcast', action, pkg, extras:[{k,v}…]}` to subscribers of `sys`. `sys.bcast.stop` unregisters it. Sending a broadcast is the existing `intent {kind:'broadcast', action, data, pkg, extras}` (see below).
- `sys.shell.exec {script, root, timeout}` — runs a shell command line (`sh -c`, or `su -c` with `root:true`, gated by the same *Allow root features* switch as packet capture and raw IP send) and answers with `{out, code}` (combined stdout/stderr, capped at 20 000 characters, and the exit code; `-1` on timeout).

## Actions that need a trusted client (network, Bluetooth, speech, phone control)

Besides SMS and contacts (above), a second set of commands needs a **trusted client** — the app's own page, or any page once *Let any page use actions* is ticked in the app Settings (off by default: these commands make the phone open sockets, pair with other devices, and control itself). Untrusted clients get `forbidden`. In the workbench: *BLE GATT / Bluetooth*, *Network*, and *Phone Control & Automation*.

- **BLE GATT** `gatt.connect {addr, phy, mtu, read, notify, max, auto, timeout}` (auto-discovers services; `read`/`notify` auto-reads every readable / subscribes to every notifying characteristic right after), `gatt.disconnect {addr}`, `gatt.discover {addr, read, notify, max}`, `gatt.read {addr, svc, chr}`, `gatt.write {addr, svc, chr, hex|text, resp}`, `gatt.notify {addr, svc, chr, on}`, `gatt.mtu {addr, mtu}`, `gatt.rssi {addr}`, `gatt.priority {addr, mode}`, `gatt.phy {addr, phy}`, `gatt.list`. Records: `{src:'gatt', ev:'connected'|'disconnected'|'services'|'char'|'read'|'write'|'notify'|'mtu'|'rssi'|'phy', addr, svc, chr, props, hex, …}` to subscribers of `gatt`. Up to 7 GATT connections at once, one operation in flight per connection (queued), 12 s timeout each.
- **Classic Bluetooth** `bt.bonded` (paired devices), `bt.bond {addr}`, `bt.unbond {addr}` (Android hides unpairing from apps on some versions — falls back to a message pointing at system settings), `bt.uuids {addr}` (SDP), `bt.connect {addr, uuid, secure}` / `bt.send {addr, hex|text}` / `bt.close {addr}` — RFCOMM / SPP client (default UUID `00001101-…` — Serial Port Profile), `bt.listen {uuid, name, secure}` — RFCOMM server, up to 4 links. Records: `{src:'btlink', ev:'open'|'accept'|'data'|'close'|'bond'|'uuids', addr, hex, text}` to subscribers of `btlink`.
- **BLE advertising** (the phone as a peripheral) `ble.adv.start {name, uuids, mfr:{id:hex}, svc:{uuid:hex}, mode, power, connectable, timeout, ext, phy}` (`ext:true` — extended advertising, lifts the 31-byte legacy limit and can use 2M / Coded PHY where the chip supports it), `ble.adv.stop`.
- **BLE scan options** (richer than Web Bluetooth): `{"sub":["ble"],"ble":{mode, legacy, phy, match, delay, name, addr, uuid, mfr}}` on the subscription message — scan mode (including `opportunistic`, piggybacking on other apps' scans), legacy vs. extended advertising, scan PHY (`1m` / `coded`), match mode, batched delivery (`delay`, ms), and filters by name / address / service UUID / manufacturer id (filtering in the radio chip itself, not after the fact).
- **Network**: `tcp.connect {host, port, timeout}` / `tcp.send {conn, hex|text}` / `tcp.close {conn}`, `tcp.listen {port, lan}` (server; `accept` records carry a new `conn`), `udp.open {port, broadcast}` / `udp.send {host, port, conn, hex|text, broadcast}` / `udp.close {conn}`, `udp.request {host, port, hex|text, timeout}` — one send-and-wait-for-one-reply (also how the DNS preset works: `host:"@dns"` resolves to the network's own first DNS server), `ping {host, count, size, ttl, timeout}` — a real `/system/bin/ping` (ICMP), `net.info` (DNS servers, gateway, interface, Wi-Fi/cellular, root availability), `raw.send {hex}` — one complete IPv4 packet sent on a raw socket via `app_process` as root (needs *Allow root features*, the same switch as packet capture). Records: `{src:'net', ev:'open'|'accept'|'data'|'close'|'ping', conn, proto, peer, hex, text}` to subscribers of `net`.
- **Speech recognition** (Android's own `SpeechRecognizer`, streaming): `speech.start {lang, partial, offline}` (`offline:true` — on-device model, Android 13+, needs a downloaded language under system Settings → Languages), `speech.stop`. Records: `{src:'speech', text, final, conf, lang}` to subscribers of `speech` — partial phrases while speaking (`final:0`), the recognized phrase once you pause (`final:1`).
- **Phone control**: `vol.get {stream}` / `vol.set {stream, pct|level, ui}` / `vol.ringer {mode}`, `tts.speak {text, lang, rate, pitch, queue}` / `tts.stop`, `clip.set {text}` / `clip.get` (Android hides the clipboard from background apps — open the DSP app first), `media {key:'play'|'pause'|'toggle'|'next'|'prev'|'stop'}`, `screen.wake {ms}`, `toast {text}`, `app.list {q, limit}` / `app.launch {pkg, root}`, `intent {kind:'broadcast'|'service'|'activity', action, data, type, pkg, cls, extras, root}`. `root:true` on `app.launch` / `intent activity` uses `am start` under root (works from the background; without root, Android only starts a window from an app that is on screen). `sys.svc {what:'wifi'|'data'|'bluetooth'|'nfc', on}` and `sys.input {kind:'tap'|'swipe'|'key'|'text', …}` (root, `input`/`svc` shell commands).
- **UI automation without root** (`ui.*`) needs the DSP app turned on once in system Settings → Accessibility (`sys.notif.dismiss {key}` needs *Notification access* instead): `ui.tap {x,y}`, `ui.swipe {x,y,x2,y2,ms}`, `ui.global {action:'back'|'home'|'recents'|'notifications'|'settings'|'lock'|'screenshot'}`, `ui.click {text}` — taps the first clickable element whose visible text matches, `ui.text {text}` — types into the focused field, `ui.screen` — dumps the visible text and tap targets (records `{src:'uitext', text, x, y, click, edit}`, then the answer with `n`).
- **System events for automation**, subscription `sys` (needs the matching access where noted): screen on/off, unlock, charging, low battery, headset plug, airplane mode, timezone/locale change, app installed/removed, Bluetooth / Wi-Fi state, a classic Bluetooth device connecting/disconnecting, phone call state, network up/down (kind, validated), the foreground app changing (`ev:'window'`, needs Accessibility), and other apps' notifications posted/removed (`ev:'notification'`/`'notification.removed'`, needs *Notification access*). Records: `{src:'sys', ev, …}`.

## Picture in picture and what the app hides

The activity supports PiP: the page calls `DspApp.pip(w, h)` (the ratio is clamped to Android's 1:2.39 … 2.39:1; `false` — no PiP on the phone) and the whole window becomes the floating one; the workbench shows only the mirror of the chosen canvas (`modules/pip.js`, works for any canvas), `dspPip(bool)` tells the page about entering / leaving; the node is drawn while it is in PiP even if the small window leaves it outside the visible area (otherwise the mirror froze), the rest of the page is hidden under the mirror, `DspApp.pipOff()` disarms the Home-button shortcut (while the mirror is open Home enters PiP instead of minimising). The WebView has no Web Bluetooth, HID or NFC (WebUSB and WebSerial are built by the app): modules that need them and the built-in presets made of them are hidden (`modules/hostcaps-kernels.js`); use the *Phone sensors* node for BLE and the USB bridge for devices.

## Live wallpaper from any canvas

The button next to ⧉ (`modules/wallpaper.js`) streams a JPEG of the chosen canvas (up to ~960 px on the long side, quality 0.8, at most every 220 ms) to `DspApp.wallpaper(base64)`, which decodes it and hands the bitmap to `LiveWallpaperService` — a `WallpaperService.Engine` that redraws the latest one it has every ~400 ms while visible, **fit** to the screen (scaled by the smaller of the two ratios, not the larger): most pictures in a patch are wide and short (a spectrum, a waterfall, a map tile) while the screen is tall, so filling the screen by cropping would blow up such a picture far more on its short side than its long one and turn it to mush; fitting instead leaves plain bars above/below (or left/right) but keeps the picture itself close to its own resolution. `DspApp.wallpaperPick()` opens the system "Set live wallpaper" chooser pointed at it (`WallpaperManager.ACTION_CHANGE_LIVE_WALLPAPER`).

Capturing the frame does **not** rely on `requestAnimationFrame`: the browser suspends rAF the moment the page itself isn't visible (screen off, another app in front) — exactly the situation a live wallpaper needs to keep working through. Instead `wallpaperTick()` (`modules/wallpaper.js`) is pulled by the DSP engine's own tick (`Eng.tick`, `core-engine.js`) — the same `AudioWorklet`-driven loop that keeps sensors ticking in the background — and while the page is hidden it also calls the target node's `draw()` directly (bypassing the normal on-screen-only redraw path) so the canvas it captures from keeps actually changing, not just the capture loop. The one real requirement: the DSP engine itself has to be running (▶ pressed) — if it's stopped, the wallpaper falls back to a plain `requestAnimationFrame` loop that only works while the page is visible. Backgrounded or killed outright, the wallpaper keeps the last frame it got, it does not go blank or crash — same rule as the microphone and camera: it needs the app's own process alive to have anything fresh to show. No browser has an API for this at all, so the button only appears inside the app (`wallpaperSupported()`).

## No CORS proxy

Inside the app the page needs no CORS proxy (*Settings → CORS proxy* is hidden there): requests to other hosts (GET / HEAD / OPTIONS: catalogues, TLE, terrain tiles, station lists, camera snapshots and MJPEG of other devices, HLS) are made by the app itself (`CorsProxy`), redirects are followed, gzip is decoded, `Range` is passed on, and the answer gets `Access-Control-Allow-*` headers; `Origin`, `Referer` and cookies are not sent, `Authorization` is. Mixed content is allowed, so `ws://` / `http://` devices on the LAN work from the https page. POST with a body is the one thing the WebView does not let an app intercept: it goes the usual way (and needs the server's CORS headers). Opened in Chrome, the page behaves as before.

## Access

The position and the sensors are behind a local port, and by request nothing is checked by default:

- **Any web page may connect** (no `Origin` check; the answers carry `Access-Control-Allow-Origin` and the Private Network Access header, so a page on https can read `127.0.0.1`). *Settings → Check the site of browsers* brings the check back (the app itself, `localhost` and the sites listed there get in, the rest get 403).
- **The token is optional**: empty — no authorization; a token (*Settings*) is required for other devices (and for this phone too with *Require the token on this phone too*).
- Only `127.0.0.1` listens until *Allow other devices on the network* is on. With no token that opens the position and the sensors to everyone on the network.
- Consequence of the defaults: any page you open in the phone's browser (and any app) can read the position and the sensors while the bridge runs. Set a token and tick the Origin check when that matters.
- Limits are the phone's own: sensors up to 1000 Hz (Android gives 200 Hz without the sensor-rate permission, which the app has), Wi-Fi scan period from 1 s (Android decides how many scans it runs).

## Staying alive in the background (automation)

The patch itself runs in the page (the engine ticks off an `AudioWorklet` pull, which Chromium does not throttle in the background the way it throttles `requestAnimationFrame` — the same reason background music keeps playing), and `BridgeService` being a foreground service keeps the whole app process, WebView included, exempt from the usual background CPU/visibility throttling. So a *Rule (If → Command)* in the patch genuinely keeps evaluating and firing commands with the screen off or another app in front — as long as the process itself survives. Two things can still kill it:

- **OEM battery optimization** (Xiaomi/Huawei/Samsung/OnePlus and others are the usual suspects) freezes or kills backgrounded apps regardless of a foreground service. *Settings → Exclude from battery optimization* asks the system for the standard `IGNORE_BATTERY_OPTIMIZATIONS` exemption (also reminded as a notification action, *Fix battery optimization*, for as long as it's not granted); on some OEM skins their own separate "autostart" / "protected apps" list needs its own manual opt-in too (search the phone's settings for it — there is no common API for this across vendors).
- **The phone rebooting** stops everything; *Settings → Start automatically when the phone boots* starts `BridgeService` again from `BootReceiver` on `BOOT_COMPLETED` — sensors and radios buffer again, the notification is back — but the *page* (where the patch and `Rule` live) is not: Android does not let a boot-time receiver open a window, only a service. Open the app once after a reboot to reconnect it; from then on it can run in the background again.

## Power, launching from outside and several windows

- **Power** (`power` subscription, node pin *power state*): `{src:'power', pct, charging, saver, thermal (0–6, Android's thermal status, 3+ severe), throttle}`. With *Poll less often…* ticked in Settings (on by default) the service slows what is polled when the battery is under 20% / 10%, power saver is on, or the phone is moderately / severely hot: sensor rate, Wi-Fi and cell scans run 2× / 4× less often (`throttle` says which; the thresholds have a 3% hysteresis so the border does not flap). Nothing is switched off — the patch only sees fewer records.
- **Wake lock and watchdog**: the partial wake lock has a 10 min timeout renewed every 20 s while a client wants something, so a hung session cannot hold the CPU; the same tick starts the server again when it has died (port busy at start, closed by the system).
- **Where the battery goes (diagnostics)**: `http://127.0.0.1:8765/status` and the `power` record now say how many clients there are, which sources are on, whether the wake lock is held, what stays open without any client (GATT connections, RFCOMM links/listener, TCP/UDP sockets, BLE advertising, a broadcast receiver, speech), the polling slow-down and the process CPU time (`cpu`, ms; the node shows it as «bridge CPU %» between two records, subscribe to `power`). With no client the notification text says `holding …`. The 40 ms flush thread of the server used to wake the process 25 times a second even when nobody listened; it now sleeps until a record arrives. After *N* minutes with no client (Settings, 30 by default, 0 — never) the service closes what clients left open (`gatt`, `rfcomm`, sockets, advertising, receiver, speech) and says so in the log.
- **Quick Settings tile** *DSP bridge*: starts / stops the bridge from the shade.
- **Open a patch from outside**: `dsp://run?patch=NAME&run=1` (an `ACTION_VIEW` intent; extras `patch`, `run`, `data` work too, e.g. Tasker *Send Intent* or `adb shell am start -a android.intent.action.VIEW -d 'dsp://run?patch=NAME&run=1'`). `patch` is the name of a patch saved in that window, `run=1` presses ▶ after it opens (the web part also understands `#p=NAME&run=1` in the page address). There is no BROWSABLE category, so a web page cannot fire the link. A whole patch in the link (`data=` — what *Copy link* makes after `#d=`) is accepted only with *Let other apps open a whole patch from a link* ticked: a patch can send SMS and open sockets through the app's page.
- **Several patches at once**: `dsp://s1`, `s2`, `s3` (same parameters) open extra windows (`Slot1Activity`…), each in its **own process with its own WebView storage** — patches saved in one window are not seen in another, and each runs its own engine. All of them talk to the one bridge service, so the sensors and radios work for the union of what the windows ask. Live wallpaper and PiP work from the main window only. The app key (`DspApp.appKey`) is now kept in the app's private folder and shared by the windows, so each of them is a trusted page.
- **Intents into the patch** (`ext` subscription): broadcast `app.dsp.phone.EXT` with extras `cmd` = `emit` (default) / `start` / `stop`, and for `emit` `name`, `value`, `text` → `{src:'ext', name, value, text}` to subscribers (number in the node's `extv`). Off until *Let other apps control the bridge* is ticked; if a token is set, the extra `token` must match. The other way round — the patch to another app — is the existing `intent` command (*Phone Control & Automation*).
- Preset: *Phone App: Power, Heat and Events from Other Apps (Tasker)*.

Not done (deliberately): a camera source (it stuttered at the service↔WebView border), running the page without a window after a reboot (Android lets a boot receiver start a service, not a window — a headless WebView in the service would be a separate, battery-hungry design), writing records to disk from the service, Wi-Fi RTT, UsageStats.

## Releases and build

The APK is built by GitHub Actions (`.github/workflows/android.yml`) **only when `tools/android` changes**; a merge into `main` publishes a release `android-v1.<run number>` with `dsp-android-1.<n>.apk` (Releases page), pull requests only build and test. The build is signed with `tools/android/dsp.keystore` (the key is in the repository, so every release installs over the previous one; it is not a store key — anyone can sign an "update" with it, keep that in mind before sharing the APK widely). The workbench inside the APK is a copy of the repository root at the build time: after changing only the web part, start the workflow by hand (*Run workflow*) to refresh it.

Locally (no Android SDK in the dev container): JDK 17, Android SDK (platform 35), Gradle 8.10+ → `gradle -p tools/android :app:assembleDebug`. The web files are copied from the repository root by the `copyWeb` task, so the app is always the current workbench.

## Checks

`cd tools/android/jvm-test && gradle runTests` — the server (handshake, masking, long frames, batching, `Origin`, preflight with Private Network Access, token) against a real WebSocket / HTTP client, the CORS proxy (gzip, redirects, `Range`, headers, errors, preflight) against a local HTTP server, the frame rotation, and the parsers (BLE advertisement, Wi-Fi channel / information elements / WPS, GNSS names and bands), on a plain JVM against the Android 14 classes (`org.robolectric:android-all`). The JS side: `node tools/test-termux.mjs`.

**Not checked on a phone:** sensors, Wi-Fi / Bluetooth scans, GNSS callbacks, the foreground service and the WebView were compiled against the Android 14 API and nothing more.

## Limits

- Android WebView has no WebSerial, WebBluetooth, WebHID or File System Access (WebUSB is built by the app, see **USB** above). For a serial device that is not USB open the workbench in Chrome and keep the app only as the bridge (`ws://127.0.0.1:8765`).
- The page itself is throttled by Android with the screen off (WebView and Chrome alike). The service keeps capturing and serving; to *process* while the phone is locked, open the workbench on another device (*Allow other devices* → `ws://PHONE_IP:8765/?token=…`).
- Wi-Fi scans are rate-limited by Android (a few per two minutes; *Developer options → Wi-Fi scan throttling* lifts it) and need Location on. Bluetooth needs *Nearby devices* (Android 12+) and Location; classic discovery and BLE scanning take radio time from each other and from Wi-Fi.
- GNSS status, raw measurements and NMEA only flow while the phone is positioning (the bridge keeps it on while one of them is subscribed). Raw measurements are not offered by every phone; a quiet `gnssraw` means the chipset does not give them.
