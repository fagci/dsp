# DSP workbench

A browser-based modular DSP lab: build signal chains by wiring nodes on a canvas. Runs fully client-side, no build step, works offline as a PWA.

**[▶ Live demo](https://fagci.github.io/dsp/)** · **[📦 Releases](https://github.com/fagci/dsp/releases)** (signed Android app) · **[💛 Boosty — support the project](https://boosty.to/fagci)**

## Features

### Workbench
- **Help** (the **?** button in the toolbar, **F1**, or the **?** in a module header; `modules/help.js`, logic in `modules/help-kernels.js`, `node tools/test-help.mjs`): the pages live in [`help/`](help/README.md) — plain Markdown, read here on GitHub and in the app from the same files, offline (they are in the service worker cache). One search box looks through the topics, the module list, the manual (this README, by section) and the presets, and it is **fuzzy**: typos and abbreviations find things (`grph`, `spectrm`, `netwrk lan`). The same fuzzy search now works in the module palette, the module picker and the patch list. A module card (the **?** in its header, or select a module and press F1) is built from the module itself — pins with their types and tips, parameters with defaults — plus the module's paragraph of this README and the presets that use it, with *Add to canvas*. `help/modules.md` is the same reference as a file (`node tools/gen-modref.mjs`). Add a page: a `.md` file in `help/` and a line in `help/README.md`. Preset «Help: Your First Patch».
- Node graph editor: pan/zoom canvas, drag-and-drop modules, typed ports (signal, number, spectrum, image, text, block, IQ stream)
- Dashboard view (split panes, draggable dividers) for building instrument-like UIs
- **Tiles-only mode**: open the app with `?readonly-tiles` (e.g. `index.html?readonly-tiles#p=My patch`) — only the tiles are shown, no sidebar, toolbar, pane headers or graph; layout and graph cannot be edited or moved, hotkeys are off, the mode is not saved. Pressing any button on a source module while the engine is stopped starts it
  - As a standalone window, only the player: `google-chrome --app="https://fagci.github.io/dsp?readonly-tiles=1"` (pin the module to a tile first)

    ![Music Player in a Chrome app window, tiles-only mode](docs/screenshots/app-winamp.png)
- **Module graph** pane in the dashboard: the regular node canvas inside a tile, next to the modules opened in other panes (SunVox-style) — see [Module graph pane](help/processing.md#module-graph-pane)
- **Detail levels (LOD)**: double-tap a module's title to collapse it to a compact card (title only), to a **dot** (a circle with initials; the full name shows on hover / when selected) or back to full. Service modules (the auto adapters *IQ → Audio*, *I/Q → IQ*) are added as dots. The **detail** button in the toolbar switches all modules at once: full → compact → dots. The level is saved in patches
- **Power profile** (⚡ in the toolbar): CPU share of every module (processing + drawing) as a badge on the module and a top-10 list, the total, and battery drain (%/h, where `navigator.getBattery` exists). Click a row to freeze a module. **skip unused** (on by default) does not compute modules whose result nobody uses: no display and no wire to a used module (outputs, sources and control modules are always kept)
- **Quick chain** (**→+** in the toolbar, enabled when one module is selected): the picker opens for the module's free signal output (a module without one — its free signal input, e.g. Sound Card), lists only what fits, connects the new module and selects it, so the next tap continues the chain — a receiver or a patch can be built with taps alone, without dragging wires
- **Module picker**: search takes several words (all must match title / id / category; titles starting with a word rank first). Drop a wire on an empty spot — or select a port and tap an empty spot — and the picker lists only modules that have a matching port, shows which pin the wire will go to and connects it on pick; modules that need an automatic *iq* ↔ signal adapter come after the exact matches. Every module gets a generated icon: initials on the category colour, the shape follows the main output type (circle — IQ, diamond — spectrum, square — records / text / images, hexagon — no outputs)
- **Wire bundles**: wires are bundled by topology, not by geometry. A module with two or more wires on one side gathers them into one harness at that side — they fan out at the pins, lie 3 px apart along the trunk and part only near their targets; wires from one module to different modules share the trunk, wires from different modules into one module converge before it. Each wire stays separate (its own colour, hover, click to delete). Automatic and independent of where the targets are: modules stacked vertically, close together or behind (a wire going backwards) are bundled as well. The toolbar button (wires icon) turns it off; the choice is remembered
- Add modules right on the canvas: double-click an empty spot (or **+** in the graph pane) and search
- Groups (nested subgraphs) with custom inputs/outputs
- Undo/redo, duplicate, multi-select, module search — from the toolbar; hotkeys: **Space** (run / stop), **Ctrl+K** or **/** (command palette: modules and patches by a fuzzy search — or a chain, `mic>fft>sa`, built with a live preview on the canvas), **Ctrl+S** (save), **Ctrl+A** (select all), **arrows** (nudge the selected modules), **+** / **−** (zoom), **Delete** (removes the selected modules) and **Ctrl+Z** / **Ctrl+Shift+Z** (undo / redo); the full list — **?** or [help/shortcuts.md](help/shortcuts.md). Patches from the side list can be **dragged onto the canvas** (or inserted with **＋**) — they are added to the current graph, not replacing it, and one Ctrl+Z takes them back
- Save/load patches to local storage or JSON files
- 160+ built-in presets: demos, quick scenarios, radio protocols, music, analysis
- Adjustable block size, sample rate and run speed (×1…×32); redraw rate switch in the settings panel (the sliders button in the toolbar, together with run speed, block size, sample rate, **All data → Export… / Import…** and the global **CORS proxy** used by Satellites, Horizon and Station Schedule — `{url}` in it is replaced by the encoded address, otherwise the address is appended): *fps max* (default; always 60 fps — the waterfall does not slow down at rest, but the main thread has less time for USB and audio), *fps auto* (60 → 30 → 20 fps as the interface sits idle, 10 fps with a USB SDR connected) and *fps min* (10 fps, lightest on CPU)
- AudioWorklet engine, SharedArrayBuffer path when cross-origin isolated
- Installable PWA with offline support; app badge while the engine runs; autosave runs in idle time under a Web Lock (no double saves from two tabs); `prefers-reduced-motion` is respected
- **Offline data** (`OfflineData` in `modules/filestore.js`): big files that modules download once — the Object Detect model and TF.js (~19 MB, `vendor/objdet/`), the JS8 text dictionary, the Natural Earth basemap — are kept in *Files → Offline data* (see the size, delete, export, or put your own file with the same name). Items marked `auto` (the JS8 dictionary and the basemap) are also fetched quietly ~20 s after start when online (not on cellular, not in data-saver mode); Object Detect loads on first use. The *⇩ offline* button in Files lists everything worth having without a network (Object Detect model, JS8 dictionary, basemap, cities, satellite TLE and SatNOGS transmitters) with a ✓ for what is already stored, and downloads the selected items; every item also has a **by hand** box for when the network is blocked: links to the sources (opened in a new tab; the app's own files such as the basemap and the JS8 dictionary are saved with a click) and *choose file…* to put the downloaded file back — models and libraries go to Files → Offline data under the right name, cities (GeoNames JSON / dump / CSV), SatNOGS transmitters (JSON) and each CelesTrak TLE group are checked and stored in their own storage (a wrong file is refused); modules add their own with `OfflineData.fileItem` / `OfflineData.item` (an `item` gives `manual()` links and `ingest(file, entry)`). They are not synced between devices and are not duplicated in the service-worker cache.
- Large patches stay smooth: nodes outside the screen are not laid out or painted (`content-visibility: auto`, enabled per node after its first layout so the size is remembered; on a 128-node test patch 4–7 → 28–54 fps)
- Built-in performance counters (long tasks/frames, slow input events, `Perf.time` marks, device profile) are appended to the error report (`core-perf.js`)

### Sources
- Oscillator, sweep/jammer, constant, LFO (a `sync` input restarts the phase on a rising edge, the `sync` output pulses at the start of every period — chain it with the oscillator's `sync` or another LFO), text source
- Microphone (stereo A+B), audio file, audio stream URL, tab/screen audio capture
- **Not from this reality** (synthetic, nothing is received): *Strange Attractor* (Lorenz / Rössler / Thomas, three outputs — try the phase scope), *Black Hole Merger* (inspiral chirp → ringdown → silence, with a `sync` pulse), *Pulsar* (period, flicker, missing pulses, scatter tail), *Schumann Resonance* (five Earth–ionosphere modes driven by lightning, a frequency multiplier brings it into the audible range), *Cellular Automaton* (Wolfram rules, rule 30 as a bit generator)
  - These are teaching models, not physics simulations. *Strange Attractor* uses the standard parameters (the largest Lyapunov exponent measured: Lorenz 0.91, Rössler 0.07). *Black Hole Merger* is the Newtonian inspiral chirp (f ∝ (t_c − t)^-3/8, A ∝ f^2/3) with a simple damped ringdown at 1.2 × the merger frequency, the duration is stretched to be audible, the noise is white. *Pulsar* has correlated flicker and a scatter tail (convolution with an exponential), but no dispersion. *Schumann Resonance* has real mode frequencies, the relative amplitudes are set by hand
- **USB SDRs** directly via WebUSB: RTL-SDR, HackRF, Airspy R2/Mini, Airspy HF+, HydraSDR RFOne, SDRplay RSP1 / MSi2500, RX-888 (mkI/mkII/mkIII) — multiple tuners/demodulators per device, wideband sweep with a panoramic waterfall, IQ recording and playback in WAV / SigMF (see [USB SDR](help/sdr.md#usb-sdr))
- **KiwiSDR** remote receivers (public list included); **SDR Receivers Directory** (Geo) puts public KiwiSDR / SpyServer receivers on the Map — click a point and its host:port goes to the KiwiSDR node (see [KiwiSDR behind HTTPS](#kiwisdr-behind-https))
- **OpenWebRX** / OpenWebRX+ remote receivers: the *OpenWebRX* node connects to `ws://host:port/ws/`, the server demodulates (AM / LSB / USB / CW / NFM / WFM), the node outputs `audio`, `rssi` and `spec` — the server's own band spectrum (FFT frames, float32 or ADPCM) on an absolute frequency axis, so it can go straight to Spectrum Analyzer. Wired the same way as **USB SDR**: `spec` → analyzer `spec`, analyzer `f1` → `tuneFreq`; the analyzer draws the channel curtain (passband, mode, bandwidth) around the tuned frequency, shows the passband under the cursor, and dragging a curtain edge sets `bw` (analog modes). `tuneFreq`, `bw` and `demod` (USB SDR names — USB, LSB, AM, NFM, WFM…) are inputs, `tuneFreq`, `bw`, `freqLo`, `freqHi` outputs; `steerFreq` is accepted and ignored (the server's band is chosen with *profile*) **Profiles** (the server's bands / receivers): the *profile* parameter (or the `profile` input — a name, id or part of a name) switches them; a switch changes the receiver for all listeners of the server, so it is never done on its own — out of the band the status lists the other profiles. **Modes** come from the server (*mode* list, only the ones its features allow); digital modes (FT8, WSPR, JS8, APRS, POCSAG, DMR, YSF, D-STAR, NXDN…) are decoded by the server: the node sets the underlying modulation (*under*, default the server's first) and the secondary mode, decoded messages and metadata go to `rec` (`kind` = `decoded` / `metadata`, `t`, the server's fields) and the last one as a line to `text`; `profile` outputs the current profile name. The delay is set by *audio buffer* (default 300 ms: that much is collected before playback and after an underrun; a backlog above three buffers is dropped) The frequency is absolute (the offset from the server's band centre is computed by the node; outside the band the status says which range the server covers); plain and IMA-ADPCM audio are supported. Same proxy rules as for KiwiSDR. Checked against the protocol of the reference client's sources and a fake server in `tools/test-openwebrx.mjs`, **not against a live server**; profile switching is not used
- Camera, video, image, accelerometer and Generic Sensor API (*Camera*: **find all cameras** lists every video input the browser exposes — extra lenses, IR / night-vision, USB thermal cameras that show up as UVC — and lets you pick one; what the browser does not expose stays invisible)
- **Motion Detect**, **Pulse (camera)**, **Timelapse**, **Color / Spectrometer** (Video): what to do with a camera picture besides looking at it — see [Camera tools](help/video.md#camera-tools)
- **Barcode / QR** (Video): reads QR codes and barcodes from a camera, video or image frame (BarcodeDetector — Chrome / Android; where the browser has none, QR codes are read by the built-in jsQR, barcodes of other kinds need BarcodeDetector): the text, a pulse on `go`, records `{format, value}`, a repeat of the same code is ignored for a set time
- **Object Detect** (Video, `modules/objdet.js`, logic in `modules/objdet-kernels.js`, `node tools/test-objdet.mjs`): finds objects (80 COCO classes: person, car, dog, cat, phone…) in a photo or video. Inputs: `vid` (live video — Camera, Video) and `img` (photo, IP Camera frames); a photo is detected once (again when a setting changes), video every *detect every* seconds. Outputs: `img` (the frame with boxes; read from the canvas only when something is wired to it), `text` (`#id label 87%` lines), `go` (pulse), `rec` (`{label, score, x, y, w, h[, id]}`, fractions of the frame), `count`, `total`. Parameters: min confidence, only these classes (`person, car`), pause between detections (counted from the end of the previous one, default 0.5 s; nothing runs while the tab is hidden), detection size (the net shrinks the frame to ~300 px anyway; default 320), picture width, advanced *compute* (auto / webgl / cpu: if the browser crashes with SIGILL on a device, try cpu — slower, but it does not touch the GPU driver), **tracking** (greedy IoU matching per class: every object keeps an id, a lost one is remembered for *keep* seconds; with tracking `go`/`rec` fire only for **new** objects, `total` counts them — people counter, door watcher). COCO-SSD on TensorFlow.js; TF.js and the model (about 7 MB) load from jsDelivr and Google storage on the first start, so the first run needs a network. For offline use put `tf.es2017.min.js` (not `tf.min.js`: it needs `unsafe-eval`, which the page CSP forbids), `coco-ssd.min.js` and the `model.json` with its shards into `vendor/` and set the advanced *script URLs* and *model.json URL*. Preset **Object Detect: Camera Video and Photo**. Checked in headless Chromium with the real TF.js and model; not tried on a real camera.
- **QR Code** (Video, `modules/qr.js`, pixels in `modules/qr-kernels.js`, `node tools/test-qr.mjs`): text (the `text` input or the parameter, UTF-8) → a QR picture on `img` (error correction L / M / Q / H, pixels per module). The generator (`vendor/qrcode.min.js`, MIT) and the reader (`vendor/jsqr.min.js`, Apache-2.0, licences in `vendor/qr-LICENSE`) load on first use and work offline. Sync devices has **Show QR** (the pair key as a link) and **Scan QR** (camera, the key is taken from the link or from plain text), so a key no longer has to be typed or sent. Preset **QR: Generator and Reader Loop (no hardware)**.
- **WebSerial on Android**: Chrome for Android has no `navigator.serial`, so `modules/webusb-serial.js` provides it over WebUSB (OTG cable): CDC-ACM (tinySA, Flipper, Pico, native-USB ESP32), CH340/CH341 and CP210x adapters — and the same shim works **inside the DSP app** (its `usb-bridge.js` gives the WebView a full WebUSB, so Serial Port works there over OTG too). Not tried on real hardware
- **tinySA / tinySA Ultra** spectrum analyzer over WebSerial: sweep into the spectrum/waterfall, screenshots, signal generator (see [tinySA](help/sdr.md#tinysa))
- **ESP-SDR (ESP32)** over WebSerial: raw I/Q bursts from an ESP32's built-in radio ([ESPARGOS/esp-sdr](https://github.com/ESPARGOS/esp-sdr) firmware), spectrum in the browser (see [ESP-SDR](help/sdr.md#esp-sdr))
- **Command Templates** (Control, `modules/flow.js`, logic in `modules/flow-kernels.js`, `node tools/test-flow.mjs`): text commands with parameters for Serial Port, Text over Network, BLE UART, MQTT Out… One template per line — `TUNE {f}`, `MODE {m}` — each `{name}` becomes an input pin of the same name (wire a knob, Cases, a number from anywhere in the graph), and every line gets a **▶ button** in the node plus a `g1…` input (a 0→1 pulse sends it). Firing builds the line — values substitute into the placeholders (integers without a dot, floats trimmed) — and it comes out on `text` (Serial Port's text input sends every change), with `go` (a pulse in the same block) and `rec` (`{cmd, text}`) alongside; a placeholder without a wired input stays visible as `{f}` in the output. Preset *Serial: Command Templates (Parameters → Serial Port)*
- Serial port (WebSerial): reads lines from the device and now sends text to it too — a `text` wire or the Send field (each line goes with `\n`; `\\n`, `\\t`, `\\xHH` escapes), e.g. commands to firmwares like [`tools/radio-bridge-esp32c5`](tools/radio-bridge-esp32c5/radio-bridge-esp32c5.ino) (ESP32-C5 Wi-Fi/BLE/Zigbee USB bridge: `MODE WIFI|BLE|ZB`, `CH`, `TX …`), **Table** (one node for lists, band plans, bookmarks, logs and the data sequencer: CSV / TSV / JSON / TXT / KML / GPX / GeoJSON, folders in the browser DB; the rows are played one by one by [Row Player](help/data.md#row-player)), Trigger Clock, Time Base — see [Table](help/data.md#table)
- **Bluetooth LE** (Web Bluetooth): **BLE UART** (Nordic UART, HM-10 / FFE0 or your own UUIDs — a serial terminal without a cable), **BLE GATT** (any characteristic: notifications or periodic read, write; formats — heart rate, battery, temperature, uint / int / float, hex), **BLE Advertisements** (RSSI, TX power and manufacturer data of one device without connecting — proximity, finding a beacon) — see [Bluetooth LE](help/phone.md#bluetooth-le)
- **IQ over Network**: a remote SDR as an `iq` source — **rtl_tcp** through a TCP → WebSocket bridge (header, rate, tuning, gain, ppm, bias-T, direct sampling are sent as rtl_tcp commands; a wire on the frequency retunes) or a **raw stream** (uint8 / int8 / int16 / float32, rate and center set by hand) from any program that writes IQ to a pipe, or **SpyServer** through the same bridge — see [Remote SDR](help/sdr.md#remote-sdr)
- **WebRTC Data**: a direct browser-to-browser channel (RTCDataChannel) with no server — the connection code (offer / answer) is passed by hand, through a messenger or the clipboard: *Create offer* on one side, *Accept offer* on the other, *Apply answer* back. Then text goes like **Text over Network** (lines, JSON into records) and the `send` input writes to the other side. Same network needs no STUN, over the internet set a STUN server. **WebRTC Tunnel** (Control) rides the same connection's `link` output and carries any `rec` records across it unchanged, encrypted by WebRTC itself (DTLS) — whatever a node on one side feeds it (Phone sensors, Network (DSP app) socket events, BLE/GATT, MQTT…), the matching node on the other side gets verbatim, so two DSP instances (e.g. two phones) can trade any graph protocol over one encrypted P2P link; several tunnels share a connection by giving each a different *channel name*. Preset *WebRTC Tunnel: Any Protocol Between Two Phones*
- **Gamepad** (Gamepad API): a gamepad, joystick, steering wheel or pedals as numbers — axes `a1…` (with a dead zone) and buttons `b1…` (analog triggers 0…1), the counts are parameters, the device is chosen by index or the first connected one; the `rumble` / `weak` inputs vibrate it. The browser shows the device only after a button is pressed on it
- **Joystick** (Sources): two sticks and eight buttons on the screen and on the keyboard — click the pad, then **W A S D** is the left stick, the **arrows** the right one, **Space, Enter, Z, X, Q, E, R, F** are buttons `b1…b8`; on a phone drag the sticks with your fingers (multi-touch) and press the buttons. Outputs: `x1 y1 x2 y2` (−1…1, with a dead zone and expo), `b1…b8`, `rec` and a ready **frame** as `text` by a template: `{x1}` −1…1, `{X1}` −100…100, `{r1}…{r4}` 1000…2000 µs (servos / RC), `{b1}…{b8}`, `{bits}`, `{hex}` (a 7-byte frame: `A5`, x1, y1, x2, y2 as signed bytes, buttons, XOR), `{n}` frame counter, `{t}` ms — wire it to *Serial Out*, *BLE UART*, *MQTT Out*, *Text over Network* or *nRF24* to drive a robot, a flight controller, a relay board or your own receiver. Frames go at *frames per second* while a key is held and once more as zeros on release (*keep-alive* repeats them at rest, a counter in the template lets the receiver notice a lost link). *hold*: a stick Y that keeps its value like a throttle. **Esc** is an emergency stop (all zeros until *Resume*). *invert vertical* turns the Y of the right, the left or both sticks over (for pitch: the down arrow / pulling back is up; the pad shows the result). The keyboard works while the pad is focused or always (not while typing in a field). A wire on `ex1…ey2` (for example from *Gamepad*) takes over that axis. Check a real machine without propellers first. Logic: `modules/control-kernels.js`, `node tools/test-control.mjs`
- **nRF24L01+** (Sources, over a USB bridge): an nRF24L01+ radio module on an Arduino Nano / Uno (or any board with the RF24 library) running [`tools/nrf24-bridge`](tools/nrf24-bridge/nrf24-bridge.ino) — the page talks to it over WebSerial (Chrome / Edge, 115200) with lines `CFG / TX / RXON / SCAN`. **Transmit**: text or hex from `send` goes out on the chosen channel (2400 + ch MHz), rate (250K / 1M / 2M), address (3–5 bytes), payload size (a fixed one pads the frame, 0 is dynamic), power, CRC and auto-acknowledge; `ok` shows whether the receiver answered. **Receive**: every packet as `rx` (text), `hex`, a pulse on `go` and a `rec` (channel, address, length, hex, text). **Scan**: the bridge listens for a carrier on all 126 channels several times and the share of hits comes out as `spec` (2400…2525 MHz) for the Spectrum Analyzer — to pick a channel clear of Wi-Fi. A wire on `ch` retunes. It talks to your own devices on your own channel and address and does not sniff other people's traffic. The firmware and the parser are checked against the protocol only (`node tools/test-control.mjs`, a simulated bridge in the browser), not on real hardware yet. nRF52 / nRF Connect boards over BLE: *BLE UART* (Nordic UART) and *BLE GATT*. Presets *Joystick: Keyboard and Screen Sticks → Serial*, *Joystick: Gamepad → Frame → MQTT*, *nRF24: Joystick → Radio Link*, *nRF24: Receive Frames*, *nRF24: 2.4 GHz Channel Scan*
- **Flight Sim** (Sources): an arcade aircraft on the *Joystick* or a gamepad, or a camera on an ADS-B aircraft; cameras chase / cockpit / tower / orbit for *Video Overlay* over *Horizon* terrain that is downloaded once and kept offline — see the node reference
- **HID Device** (WebHID): any USB / Bluetooth HID device without a driver — foot pedals, remote controls, USB scales and sensors, barcode scanners, your own boards (Leonardo / Pro Micro, RP2040). Input reports as hex and as records, one field of the report as a number (offset, format, bit, scale, report id filter), the `send` input writes output or feature reports. Keyboards and mice are closed to WebHID by the browser
- **FUNcube Dongle Pro+** (WebHID, `04d8:fb31`): tuner control — frequency (with ppm correction), LNA, mixer gain, IF gain 0–59 dB, bias-T, RF / IF filters; outputs `fc` for the `fc` input of **I/Q → IQ**. The IQ itself comes as USB audio: **Microphone** in *stereo device* mode at 192000 Hz, then **I/Q → IQ** (preset *FUNcube Dongle Pro+: Receiver*). The original FUNcube Dongle Pro (`fb56`) has a different command set and is not supported
- **Speech to Text** (Web Speech API — Chrome / Edge / Safari, the browser's own recognizer, listens to the default microphone, not a graph signal): every phrase as `text` and as a `rec` `{text, conf, lang}`, a pulse on `go`, interim text in the readout, language by a code (`ru-RU`)
- **NFC** (Web NFC, Chrome on Android over https): read NDEF tags — serial number, the first text / URL / JSON record as text, every record as a `rec`; write text, a URL or JSON to a tag (the *Write* button, a pulse on `go`, or a text on the `write` input)
- **MQTT In** (over WebSocket, QoS 0/1, username/password, auto-reconnect): subscribe to topic filters (`+` / `#`); a message comes out as text, topic, a number (the payload itself, or a JSON field — `temp.value`) and as records (a JSON object or array becomes `rec` with the topic added, so Tasmota / ESPHome / Home Assistant sensors with lat / lon go straight to the map). The browser cannot open `mqtt://` itself: give the broker a WebSocket listener (Mosquitto `listener 9001` + `protocol websockets`, EMQX, HiveMQ, the Home Assistant add-on); from the https page only `wss://` works — see [MQTT](help/protocols.md#mqtt)
- **Messenger** (Sources; `modules/msgr.js`, protocols `modules/msgr-kernels.js` + `msgr-session.js`, `node tools/test-msgr.mjs`, `node tools/test-msgr-net.mjs`): one node for thirteen ways to talk and to read — **Nostr** (public relays `wss://…`, the channel is a hashtag; events are signed with BIP-340 Schnorr, `nsec` / hex key or a new anonymous key per session, incoming signatures are verified), **ntfy** (topic over HTTP, token or user:password), **Matrix** (homeserver, password or access token, a room id or alias, joins it itself), **Telegram** (a bot from @BotFather: long poll, replies go to the last chat or a fixed one), **IRC** (`wss://` straight from the page, or `ircs://host:6697` through the Node bridge), **XMPP** (account `user@domain`, STARTTLS + SASL PLAIN, MUC room; a password is never sent without TLS unless *plain* is ticked; needs TCP — see below) and **APRS-IS** (needs TCP: *user* is the callsign, *channel* the server filter — `r/lat/lon/km`, `m/km`, `b/CALL*`, default messages to you; stations come out as records with `lat` / `lon` — wire `rec` to *Map*; messages are written `@CALL text`, acknowledged and retried like on air; with no passcode it is receive-only — the passcode of a callsign is entered by its licensed owner, it is never computed for you) and **Email** (needs TCP: *server* `imaps://host:993` — new mail in the mailbox *channel* comes out as `[subject] text` (MIME, base64 / quoted-printable, charsets, RFC 2047 names), read with `BODY.PEEK` so nothing is marked as seen; *smtp* `smtps://host:465` or `smtp://host:587` with STARTTLS — a letter is written `@name@host subject⏎text`; the mailbox is polled every *poll* seconds; the password is never sent without TLS) and **SMS** (the phone's own text messages through the DSP app for Android — no Node bridge: the page of the app connects to the phone's socket, `server` empty = `ws://127.0.0.1:8765`; incoming SMS come out as `from number: text`, a message is written `@+79001234567 text` and goes out as an SMS from the phone (the app asks for the SMS permission and sends at most 5 a minute); only the page of the app has the key, other sites get `forbidden`) and **Reticulum / LXMF** (`modules/rns-kernels.js`, `node tools/test-rns.mjs`; Every post is a record `{id, from, name, text, url, tags, lang, avatar, image, likes, boosts, replies, cw, boost_by, t}` — wire `rec` to a **Table**: a list `feeds/radio` in the browser database keeps it (key `id` — a post seen twice is one row, *max rows*, *newest first*, cards), survives a reload, is backed up and synced; filter it there (`tags:antenna`, `lang:ru`, `likes>10`). *also fetch…* sets how far back the first read goes (0 — only what comes later); **RSS / Atom / JSON Feed** (*server* — feed addresses, several separated by a space; *channel* — words: any of them in the title, text or categories, `-word` drops an item; polled every *poll* seconds, at least 60; RSS 2.0, Atom, RSS 1.0 / RDF and JSON Feed are read, a truncated or sloppy feed as far as it goes, DTD entities are never expanded; the record adds `title`, `summary`, `feed` — a headline is the `text` for Chat). **A browser cannot read most feeds (no CORS headers)**: set the *TCP gateway* to a **Node bridge** — it fetches the feeds itself (`--hosts` limits which servers), or tick *through the CORS proxy* (Settings; the bridge is one too, see *CORS proxy of the Node bridge* and *Devices*), the Android app needs nothing. **Where TCP comes from** (IRC `ircs://`, XMPP, APRS-IS, email — a browser cannot open sockets): inside the DSP app for Android the phone itself (`tcp.connect` with `tls` / `starttls`, certificates checked by Android's store; *via* `auto`); from any other page — one *bridge* address (the «TCP gateway»), which is either the DSP app of a phone (`ws://192.168.0.5:8765`; tick *Let any page use actions* in the app Settings) or the Node bridge (`ws://127.0.0.1:8777`) — the node tells them apart by the greeting. Inputs `send` (a message) and `to` (a recipient/chat; empty — the channel), outputs `rec` (`{t, proto, dir, from, to, text}` — wire to *Chat*, its «my name» = the node's nick), `text`, `from`, `new`, `ok`. Your own messages come back as outgoing (by the server where it echoes them, locally where not). *history* also fetches the last N seconds, *reconnect* retries with a pause, *via* picks where the protocol runs (auto: in the page, through the bridge only where a TCP socket is needed). The presets *Messenger: One Chat for Nostr, ntfy, Matrix, Telegram, IRC and XMPP* and *APRS-IS: Messages and Stations on the Map* and *Email: Mailbox as a Chat (IMAP / SMTP)* and *SMS: Texts as a Chat (DSP app on Android)* *Reticulum: LXMF Messages over a Mesh (Sideband / NomadNet compatible)* and *Feed: Mastodon and Bluesky by Tags into a Table (cards)* and *Feed: RSS / Atom News by Keywords into a Table (cards)* show it.

- **CORS proxy of the Node bridge** (`node tools/test-proxy.mjs`): the same bridge answers `GET /proxy?token=…&url=<address>` — so **one line in Settings → CORS proxy**, `http://127.0.0.1:8777/proxy?token=TOKEN&url={url}` (or `http://<device>:8777/…` for a bridge on another machine), gives every module that has a *through the CORS proxy* tick (IP Camera, IPTV, Stream Check, Internet Radio, Packet Link, RSS…) and every module that always uses the proxy (satellites, terrain, schedules…) a proxy of your own instead of a third-party service that would see every address you open. GET and HEAD, `Range`, redirects (each hop is checked again), and **streams are passed on as they come** (MJPEG, HLS, radio — closing the page closes the target). The page gets CORS and Private Network Access headers, also on errors, so a refusal can be read. Protection: the page's *Origin* and the token are checked (`--origin`, `--token`), `--hosts` limits the targets, and by default the bridge refuses loopback, link-local (cloud metadata `169.254.169.254`), unspecified and multicast addresses — checked on the address actually connected, so a name that resolves to one is refused too, and after every redirect; the local network (cameras) is allowed, `--proxy-no-private` closes it, `--proxy-loopback` opens loopback (e.g. a camera server on the bridge machine), `--no-proxy` turns the endpoint off. The page's cookies and authorization are not passed to the target, its cookies are not passed back. An `http://` bridge on another machine is mixed content for an `https://` page: allow it in the browser or serve the bridge over https.
- **Certificates, `wss://` and `https://`** (`modules/cert-kernels.js`, `tools/node/tlsdir.mjs`, `node tools/test-cert.mjs`, `node tools/test-bridge-tls.mjs`): a page on `https://` opens `ws://` only when the browser is told to allow insecure content; `wss://` needs a certificate the browser trusts. Two ways to get one, both with **your own CA** (no third party, works for names and IPs of your local network): (1) the Node bridge does it itself — `node tools/node/bridge.mjs --tls` makes a CA and a certificate in `~/.dsp-bridge` (`--tls-dir`), for its host name `.local`, `localhost`, `127.0.0.1`, `::1` and the LAN addresses (`--tls-name pi.lan --tls-name 10.0.0.7` adds more), renews it when the addresses change or a month is left, serves **`ws://` and `wss://` (and `http://` / `https://`) on the same port** and the CA at `http://<address>:8777/ca.crt` (public, never a key); it prints the CA SHA-256 fingerprint to compare when you install the CA; `--cert FILE --key FILE` uses your own files (mkcert, Let's Encrypt) instead; (2) **Settings → Devices → Certificates** makes them in the browser: type the names and IPs of a server, press *Create certificate* and get `<name>.crt` (with the CA chain), `<name>.key` and `dsp-ca.crt` for any server that speaks TLS; the CA is made once and kept in the browser — its private key sits in IndexedDB as a **non-extractable key** (page code can sign with it, nobody can read it out), *Forget this CA* removes it. **Trust the CA once** on each device that opens the page (Chrome / Edge: Settings → Privacy and security → Security → Manage certificates → Authorities → Import; Android: Settings → Security → Install a certificate → CA certificate; iOS: install the profile, then Certificate Trust Settings; desktop OS: the keychain / certificate manager) — after that a `wss://pi.lan:8777` device from the list works without *allow insecure content*. **The CA is limited by name constraints** to `localhost`, `.local`, `.lan`, `.home.arpa`, `.internal` and private / loopback / link-local networks, so even a leaked CA key cannot vouch for a public site (OpenSSL and the browsers enforce it; checked with `openssl verify` and real TLS handshakes). Certificates are ECDSA P-256 / SHA-256, a year long, the CA ten. **The Android app can speak `wss://` too**: the phone makes its own key and keeps it (it never leaves the phone); *Settings → Devices → Certificates → Install on the device* takes a device of the list, asks the app for its public key (`tls.csr`), signs a certificate for it with your CA (the names / IPs of the field, or the address of the device) and sends back only the certificate (`tls.install`) — then `wss://<phone>:8766` opens (the plain `ws://…:8765` keeps working; *Test* shows the TLS port), *Remove from it* wipes the key and the certificate. A certificate for a key other than the phone's is refused by the app. An *unconstrained* CA (for decrypting the traffic of your own device in the VPN mode) is supported by the generator (`certNewCA({constrain:false})`) but is not offered in the UI yet.
- **Proxy mode** (Settings → *Proxy mode*, next to *CORS proxy*): **always** — everything that uses the proxy goes through it (the old behaviour, and the default); **on error** — directly first, and only when the browser refuses a request to another site (CORS, or an `http://` address from an `https://` page) the same GET / HEAD is repeated once through the proxy; a host the proxy helped is remembered for the session and goes through it at once — so a proxy that sees your addresses is used only where it is needed (and if the proxy fails too, the original error is shown, not the proxy's); **off** — the proxy field is ignored. - **Source Locator: levels, bearings and distances** (`use: auto` takes whatever the records carry): besides signal levels (path loss, the unknown power is fitted) and bearings, a record may carry a **distance** — fields `dist` (m) and `distSigma` (m): **Wi-Fi RTT** (802.11mc, the Network node's `wifi rtt`; the app now gives these records the position and the same `dev` key as the Wi-Fi scan, so they join the AP's other marks) and the **Timing Advance** of the serving LTE / GSM cell (a ring at 78 m / 553 m steps: `termuxTaDist`). - **Gain Optimizer (max SNR)** (Radio; `modules/gainopt.js`, kernel `gainopt-kernels.js`, `node tools/test-gainopt.mjs`): finds the receiver gain with the best SNR of one target. Wire the receiver `spec` to its `spec`, `clip` (USB SDR ADC clipping, %) to `clip`, its `gain` to the receiver `gainDb` (and to the Spectrum Analyzer `gain`); `f` takes the target frequency, otherwise the strongest signal (not the edges and the centre hump) at the start. A run steps the gain from *gain from* to *gain to* by *coarse step*, waits *wait after a change* ms (the hardware applies gain with a delay), averages the target's SNR (peak in ±*target window* over the median floor around it) over *frames*, stops climbing at the first step whose clipping reaches *overload*, then with *refine* walks 1 dB steps around the best (not into the clipped zone). The pick is the best SNR without clipping; within *prefer a lower gain within …* dB of it the lowest gain wins (headroom); *back off* subtracts a margin. Start with the button or a pulse on `run`; *repeat every* s re-runs it (it moves the gain — not while listening). Outputs: `gain` (stays at the result), `best`, `snr`, `busy`, `done` (pulse), `rec` (a record per step and a final one), `text`; the readout lists every step. Wide signals (broadcast FM) need larger guard / training bins, so it is meant for narrowband services. **View**: the wheel on a pane zooms (around the cursor), drag pans a zoomed pane, double click resets it; more ranges than *panes* are paged with ◀ ▶ (bottom right), the wheel on a pane title, or by themselves — *follow* turns the page after the Band Scanner (a manual page-turn pauses it for 10 s); every range keeps its own data while it is off screen. **Humps**: the edges of a receiver window droop, so a wide range stitched from windows shows a hump per window — *edge* (% of the window dropped on each side, 10 by default) on the analyzer and the same value on the Band Scanner (which then steps by the useful middle and starts the range with it) remove them. The edge of a window is still used where no other window has covered the range yet, so there are no gaps. The Band Scanner also learns the receiver's centre offset (*shift center off DC* and AM/SSB put the window `sr/4` above the requested frequency): it asks for `freq − offset`, so windows stand exactly on the range and narrow ranges are not missed. The preset keeps *fast retune* off and *settle* at 250 ms. The preset sets the receiver squelch to *input* (the `sqlGate` wire from the Band Scanner's `listening`): the speaker is silent while the scanner moves and opens only when it stands on a signal (or is parked on a marker); *squelch hang* keeps it open a little after. **Revisit rate**: the Band Scanner's *order* — *band by band* (the default) walks one range to its end before the next, so a wide range keeps the narrow ones waiting (a 16 MHz range takes ~9 windows, plus the listen timeout on every signal that is not skipped); *interleave* takes one window of every range in turn (`V L P V L P …`), so every pane is refreshed at the same pace and a wide range simply takes more rounds. **Scan non-stop until a marker**: *park the scanner on a marker* gives `holdF` — the frequency of the first marker that is set — which the Band Scanner takes on its `hold` input: it moves the window onto that frequency and stands there until the marker is cleared with its × — then the scan goes on from where it stopped. Without wiring `count` to `active` the scan is non-stop as well. **Gain by stages (RTL-SDR)**: USB SDR → advanced → *RTL gain mode*. *default* is the usual *auto* / *gain, dB* (LNA and mixer share one slider, VGA is fixed at step 8 = 16.3 dB); *stages* gives the R820T/R828D stages separately, as in r820tweak: *LNA step*, *mixer step* and *VGA step* (0–15 each; LNA and mixer can be left to the chip's own AGC with *LNA auto* / *mixer auto*). The readout shows `gain L9 M8 V8 ≈ 32.8 dB` in the same scale as the *gain, dB* slider (VGA step 8 adds nothing; another step adds or removes its difference). Handy against overload (the readout warns about it): lower LNA and mixer, keep VGA. Switching back to *default* restores the stage registers; with VGA step 8 the registers are identical to *gain, dB* of the same value. **Pattern that repeats with the window step**: the Band Scanner learns the receiver's centre offset from `freqLo` / `freqHi`; right after a retune those still show the previous window, and when the retune takes longer than *settle* a wrong offset was learned (e.g. −0.46 MHz) — the windows then jumped back and forth instead of stepping evenly, with spikes and humps at the seams. Vertical drag on a pane shifts its range, Ctrl+wheel (or a vertical two-finger pinch) scales it, the **⇕ dB** button (bottom row) fits every pane to its own data (noise −8 dB … peak +8 dB); a double click / double tap resets zoom and dB range of the pane. The ranges are stored in the patch. The preset now uses *settle* 90 ms, *fresh frames* 2, *edge* 15 %. **Pattern with fast retune on**: with *fast retune* the PLL gets no waiting time and the first frames after a retune can carry a not yet settled frequency (the spectrum is shifted, and a wrong trace stays in peak hold). Now the receiver waits at least 15 ms before it counts a retune done, the panes drop the first frame after a window change, the scanner's *fresh frames* 0 now means the minimum of 2 (the first one is dropped by the panes, the second is recorded) — raise it to 3–4 only if the detector has to confirm signals, and the **⌫ peak** button (bottom row) clears the peak hold. The PLL lock bit read right after the register burst still showed the previous frequency, so a retune could count as done while the synthesizer was not locked: fast retune now waits 4 ms before the lock check and keeps the 8 kHz autotune step (≈7–8 transfers instead of ≈6; the final registers are the same as the full procedure). The wheel zoom of the panes is 5× slower. If the pattern is still there, switch *fast retune* off and keep *settle* ≥ 100 ms. **Why a scan can look stuck**: (1) the scanner is *parked* — a marker was set (a tap on a pane places one, a double click is two taps) while *park the scanner on a marker* is on: the panes now show a «⏸ scan parked on marker … » plate and a **▶ resume** button (clears the markers); the **⏸ park** button in the bottom row switches the parking on and off, and the taps of a double click (zoom reset) no longer leave a marker; (2) the Band Scanner's *loop* is off — one pass and it stops on the last window («done» in its readout); (3) *fresh frames* was 0 with the old patches: now 0 means *auto* — 3 frames when `spec` and `active` are wired, so the detector can confirm a signal (set 1–10 by hand, or unwire `spec` for a timer only); (4) the detector in the panes looks for narrow signals (guard 4 / training 32 bins): a wide plateau (a CDMA/LTE carrier, hundreds of kHz and more) is not marked. **Several receivers at once (up to 4)**: preset *USB SDR ×4: Multiband Scan (4 receivers)*. Every Band Scanner gets `lanes` = number of receivers and its own `lane` (0…lanes−1): the list of all windows (in the chosen *order*) is common and a lane takes every `lanes`-th window, so neighbouring windows are received at the same moment and a pass is ~`lanes`× shorter. The Spectrum Analyzer takes the receivers on `spec`, `spec2`, `spec3`, `spec4` and draws them in the same multiband panes; each receiver has its own Signal Detector (frames of different receivers do not break each other's confirmation) whose `count` / `f1` go to its scanner and to the receiver's `tuneFreq`; all `bands` outputs may go to the same `sigs`. A waterfall row of a wide range is finished when the windows of all receivers have covered it. Several identical dongles (the same serial) are fine: each USB SDR node takes a free one (a node reconnects to the same dongle only when the serials differ — `rtl_eeprom -s`). Use one sample rate; mind the USB hub (4 × 2.4 MS/s ≈ 19 MB/s). **Waterfall of the panes**: A waterfall row is now built strip by strip while the scanner passes the range, and the waterfall shifts down **only when the pass is over** (a range wider than a window: when the scanner comes back to the start; a range that fits into one window: one row per visit, and one row every *waterfall row interval* while the receiver stands on it). Note: with the Band Scanner's *loop* off the scan ends after one pass («done» in its readout) and the receiver stays on the last window. **Why a short *settle* did not work**: after a retune the USB queue (8 transfers × 25 ms) still returns ~200 ms of samples of the old frequency, which are dropped, and only then comes the spectrum of the new window; and the detector needs 2 frames of the new window to confirm a signal — a scanner that moves on after 60 ms sees no new frames at all (no waterfall rows, no detections). Two changes: while retunes are frequent (≥3 in 3 s) the receiver reads 5 ms chunks (200 reads/s instead of 40, the old-frequency backlog is ~40 ms; it goes back to normal when the scan stops), and the Band Scanner has a `spec` input and *fresh frames* (default 0 = timer only; the preset wires `spec` and uses 3): it decides only after that many spectrum frames **of the new window** (centre equal to the requested one), *settle* is then just a minimum wait (can be 0–60 ms). **Faster retuning (RTL-SDR)**: a tuning used to cost ~23 sequential USB control transfers (every tuner register was rewritten, even when it did not change). Now a register that already holds the value is skipped, and the PLL registers go in one burst — the same final register state with about half the transfers (≈12). The *fast retune* option (USB SDR → advanced; on in the Multiband Scan preset) goes further, like the `fast_retune` branch of rtl-sdr: no VCO fine-tune read, no switch of the PLL autotune to 8 kHz, no dummy read after the demodulator I2C switch — ≈5–6 transfers; the PLL lock is still checked and a failed lock falls back to the full procedure. After that the scanner's *settle* can be lowered (the receiver needs less time, the spectrum frames after a retune are the limit). Wide sweeps (*sweep*) get faster too. A pane title shows how long ago the range was last updated (after 3 s) and the scanner readout names the order in use — handy to see the revisit pace, and which version of the patch is running (an old saved patch keeps *band by band*; set *interleave* by hand). The scanner decides «a signal / move on» only after the receiver window actually stands on the requested centre, so frames of the previous window do not hold it for the listen timeout. A skipped signal is at least one channel wide (the range's `step`, 12.5 kHz without one), because a carrier drifts and a narrower skip loses it. **Search and skip**: a ▼ on a pane marks a signal of the Signal Detector (`sigs`), its `count` stops the scanner on it. A signal that should not stop it: *Blacklist found signals* on the detector, or a Table with `lo` / `hi` rows on its `skip` input (pagers, beacons). ### Processing
- Filters, gain, mixers (4/12 ch), AGC, squelch, mains notch, adaptive hum canceller (tracks mains frequency, all harmonics), comb notch, adaptive filter, spectral denoiser
- **Echo Canceller (AEC)** (Audio, `modules/aec.js`, logic in `modules/aec-kernels.js`, `node tools/test-aec.mjs`): removes from the microphone what the speaker played. Inputs `mic` and `ref` (what plays on the speaker / the far end, or a second microphone near a noise source): a partitioned-block frequency-domain adaptive filter (PBFDAF, overlap-save) learns the path ref → mic (delay and room tail up to 512 ms), converges in ~3 s (≈24 dB at 3 s, 50+ dB later on a synthetic path), keeps the near voice during double talk (adaptation slows when the error is loud; the first 2 s of an active reference adapt without that gate) and a soft suppressor removes the residual. Outputs `out`, `echo` (what was removed), `erle` (dB), `delay` (the path found, ms). **One microphone** (`ref` not wired): the filter predicts the signal from its own past later than *remove repeats later than* (20…400 ms) and subtracts it — echoes, a repeater that doubles the signal, long reverb; the voice itself stays (a sustained tone or a strongly periodic sound is predictable too and gets reduced, so keep the delay above the pitch period). Delay of the node: 256 samples (5.3 ms at 48 kHz); cost 3.5 % of a core for 128 ms, 7 % for 512 ms at 48 kHz (measured in Node).
- **Voice Restore (de-mumble)** (Audio, `modules/voicerestore.js`, logic in `modules/voicerestore-kernels.js`, `node tools/test-voicerestore.mjs`): for speech that went through a narrow filter and sounds muffled / mumbling / boomy. It learns from the speech itself (about 1 s of active speech): the long-term spectrum in ⅓-octave bands is compared with a typical speech spectrum (LTASS shape) and the bands are corrected (boost up to *max boost*, cut up to 12 dB; bands near the noise floor are not lifted), then the top that is missing above the found cut-off is rebuilt by shifting the lower octave up and shaping it like speech (the rebuilt top is plausible, not the original; on a synthetic test the spectral error of a 1.2 kHz wall dropped 20.6 → 12.3 dB with the equalizer and → 6.6 dB with the extension; speech that already has a typical spectrum changes by < 0.2 dB). Parameters: equalizer strength, extension, rumble cut (24 dB/oct below *boom*), max boost, learning time, bypass; output `cut` (the cut-off found, Hz). STFT with 75 % overlap, delay N samples (21 ms at 48 kHz). A mains hum or a drone: put the *Hum Filter* before it. Not a neural network: a blind equalizer plus bandwidth extension.
- **Neural audio** (`modules/nnaudio.js`, streaming wrapper in `modules/nnaudio-kernels.js`, `node tools/test-nnaudio.mjs`; models run in the browser, no network needed): **Denoiser (RNNoise)** (Audio) — a small recurrent network (112 KB WASM, `vendor/rnnoise.wasm`, Xiph RNNoise 0.1 built by Jitsi) that suppresses noise in speech; `in` → `out`, `mix` (0…1), outputs `vad` (speech probability) and `speech` (1 above the threshold). 10 ms delay; the net works on 48 kHz frames, other engine rates are resampled (linear). It needs a few seconds to learn stationary noise. Big models of this family are kept in Files → Offline data and listed under *⇩ offline*.
- **Sound Classifier (YAMNet)** (Analysis, `modules/yamnet.js`, logic in `modules/yamnet-kernels.js`, `node tools/test-yamnet.mjs`): Google YAMNet through MediaPipe Tasks Audio (WASM, in the browser) names the sound in a ~1 s window out of 521 AudioSet classes (speech, music, siren, engine, dog, white noise…). Input `in`; outputs `text` (top classes with shares), `label`, `score`, `hit` (1 while a class from *watch for* is heard — substring match, e.g. `speech` also catches «Male speech»), `rec` (an event when a watched class appears). Parameters: classify every, classes to show, min share, watch list, watch threshold. The window is averaged down to 16 kHz exactly (15 600 samples). ~11 MB (`vendor/mediapipe/`: MediaPipe 1.1.1 wasm + `yamnet.tflite`) are fetched once into Files → Offline data and listed under *⇩ offline*; SIMD build only.
- **Speech to Text (Whisper)** (Analysis, `modules/whisper.js`, logic in `modules/whisper-kernels.js`, worker `whisper-worker.js`, runtime in `vendor/whisper/`, `node tools/test-whisper.mjs`): OpenAI Whisper (ONNX, q8) through Transformers.js + ONNX Runtime Web (WASM, in a separate thread — the graph does not stall). Input `in`; the stream is cut into phrases by pauses (threshold in dBFS plus a self-adjusting noise floor, pause, longest phrase 5…28 s), each phrase is recognised: outputs `text` (last phrase), `full` (transcript), `go` (pulse per phrase), `rec` (event with text and time), `count`, `busy` (phrases waiting). ~100 languages (Russian included), *language* auto or fixed (fixed is more reliable on radio), *translate* to English; models tiny (≈45 MB) / base (≈85) / small (≈270) / large-v3-turbo (≈800 MB, the most accurate, needs a fast PC) and the `.en` variants; *norep* fights word loops (the decoder bans repeated 5-grams, long runs of one word are collapsed); or any ONNX Whisper repo from huggingface.co in *own model repo*. Typical Whisper inventions on silence («Thank you.», `[BLANK_AUDIO]`, loops) are dropped (*junk* option); optional `[m:ss]` stamps; buttons *Transcribe file…* (audio/video, faster than real time), *Clear*, *Save text*. The runtime (≈15 MB, `vendor/whisper/`) and the model files are fetched once into Files → Offline data (⇩ offline: runtime + tiny) and then work without a network; the worker never goes to the network itself — the page serves it the files. If huggingface.co is not reachable from the network, in Files → Offline data every item with http sources has a *by hand* section: open each link in a new tab (the browser saves the file), then *choose downloaded files…* and pick them — the names are matched (for Whisper `.onnx` go to `onnx/`) and the files land in Files → Offline data (`OfflineData.save`). The model shows up in the ticker via `rec`. See the preset «Speech to Text (Whisper)».
- **Notes (Basic Pitch)** (Analysis, `modules/pitchnn.js`, logic in `modules/pitchnn-kernels.js`, `node tools/test-pitchnn.mjs`): Spotify's Basic Pitch (TF.js, ~0.9 MB model in `vendor/basicpitch/`) hears several notes at once. - **Meteor-M LRPT** (137 MHz) from raw IQ, frame level: QPSK/OQPSK demodulator, CCSDS decoder (Viterbi K=7, NRZ-M, ASM, derandomizer, RS(255,223)×4) → VCDU frames → **MSU-MR image** (packets, JPEG-like 8×8 segments, RGB composites, PNG) (see [Meteor-M LRPT](help/satellites.md#meteor-m-lrpt))
- **Radiosondes: Vaisala RS41** (400–406 MHz) from raw IQ or FM audio: serial, position, height, climb, speed, temperature, humidity → map (see [Radiosondes](help/radio.md#radiosondes-rs41))
- **Inmarsat STD-C** (1.5 GHz): BPSK 1200 → frames → packets → SafetyNET / FleetNET EGC messages (see [Inmarsat STD-C](help/radio.md#inmarsat-std-c))
- **Inmarsat Aero** (1.545 GHz, P channels 600 / 1200 bit/s): MSK → sync word → Viterbi frames → signalling units with CRC → system tables, voice-channel assignments (aircraft, frequencies) and ACARS over satellite; a scanner decodes all carriers of a wideband recording at once (see [Inmarsat Aero](help/radio.md#inmarsat-aero))
- **MPT 1327** (analogue trunking control channel): FM → FFSK 1200 Bd → codewords with CRC → PFIX/IDENT (see [MPT 1327](help/radio.md#mpt-1327))
- **ISM 433 MHz** (sensors, remotes, doorbells; OOK and FSK): pulse train → PWM / PPM / Manchester → EV1527/PT2262, Nexus, or an unknown packet with timings and bits (see [ISM 433](help/radio.md#ism-433))
- **LoRa** (chirp spread spectrum, SF7–12, 7.8–500 kHz): decoder (preamble, sync word, SFD, header, Hamming, interleaving, CRC; measures SNR and carrier offset) and modulator (text or hex → IQ, also to HackRF TX) (see [LoRa](help/radio.md#lora))
- **AIS** (marine VHF, 161.975 / 162.025 MHz): GMSK 9600 Bd → HDLC with CRC → position reports, static data, base stations and aids to navigation; vessels on the map with name, type and size, `!AIVDM` sentences on a text output (see [AIS](help/radio.md#ais))
- **POCSAG** pagers (512 / 1200 / 2400 Bd, 2-FSK): FM → BCH(31,21) codewords with error correction → RIC, function, text and numeric messages, tone-only calls; to the Messages node (see [POCSAG](help/radio.md#pocsag))
- **ACARS** (VHF 131 MHz, AM + MSK 2400 Bd): envelope → MSK → blocks with CRC and parity → aircraft registration, label, flight, text (see [ACARS](help/radio.md#acars))
- **Digital Voice Decoder** — one decoder for **DMR, P25 Phase 1, NXDN 9600 and 4800, YSF, M17, D-STAR and dPMR**: the protocol is found by its sync words (or picked by hand), records and raw vocoder frames on separate outputs, turned into sound by the mbelib [Vocoder](help/radio.md#vocoder-mbelib) (see [4FSK Digital Voice](help/radio.md#digital-voice-decoder-4fsk))
- **TETRA** (base-station downlink, π/4-DQPSK 18 kBd, 25 kHz channels): sync burst → cell (MCC / MNC, colour code, frequency, location area, services), slot timing, AACH, calls by usage marker, MAC-RESOURCE addresses and channel allocations, names of LLC / MLE / MM / CMCE messages, SDS text / status / positions (Messages, Subscribers, map), speech of traffic slots (see [TETRA](help/radio.md#tetra))
- **DMR** (Tier II / III, repeater, mobile or direct mode): 4FSK 4800 Bd → colour code, time slots, voice calls (from → to, emergency, encrypted, talker alias), CSBK, data and SMS, raw AMBE+2 frames (see [DMR](help/radio.md#dmr))
- **Analog video** (FPV 5.8 GHz, broadcast and satellite TV) from raw SDR IQ: FM / AM demodulator → composite video → line and field sync, PAL / NTSC, colour, interlace → picture (see [Analog video](help/video.md#analog-video))
- Building blocks: CRC, scrambler, interleaver, convolutional encoder / Viterbi, sync word search, async serial, NRZ clock, text ↔ bits

### Music
- Synths (2 osc, 4 voices), acid bass (303), drum sequencer, Files › audio (sample library) with an audio editor (see [Sample editor](help/media.md#sample-editor))
- **Tracker**: plays and edits MOD (ProTracker), S3M (Scream Tracker 3) and XM (FastTracker 2); split into graph nodes: song, single channels, instruments played by your own generator modules, pattern view, and every editor panel as its own node — lay them out in dashboard tiles as your own Renoise-style editor (see [Tracker](help/media.md#tracker))
- **Sampler**: polyphonic (4 voices) player of clips from Files › audio, pitched by `freq` — plays from the tracker, piano roll or MIDI
- Piano roll, step sequencer, generative melody, arrangement playlist, master clock
- **Studio** is a set of ordinary graph nodes and wires; there is no separate studio. Data lives in the nodes, editors live inside the nodes, everything is wired (`modules/studio-*.js`; data and presets in `studio-kernels.js`, block DSP in `studio-dsp.js`, `node tools/test-studio.mjs`, `node tools/test-studio-dsp.mjs`).
  - **Song (Studio)** holds a composition (patterns, channels, playlist, mixer), **loads** it (8 example songs, Files › Songs, a `.json` file) and **saves** it (💾 Files › Songs, `⬇ .json`); the pin `song` (its own port type) goes to the blocks that depend on the composition. They edit the shared song, the node keeps it; the other blocks refresh by themselves. Without the `song` wire a block works on its own data.
  - **Pattern Playlist (Studio)**: pattern blocks on 8 lanes; lane k gives `gK` (a clip is playing) and `pK` (its pattern index, `-1` while no clip plays — one wire to a Drum Machine / Piano Roll `pat` and to the Mixer `scene`), `bar`, `step`, `end`, loop region; `clk` / `run` / `reset` in.
  - **Drum Machine (Studio)**: step grid, steps on `clk` (Master Clock) or its own bpm, `pat` picks the pattern (negative = silent), a gate pin per row `g1…g8` (a trigger for a Sampler or any gate input), built-in drum sounds and clip rows (a sample from Files › audio) on `L` / `R` / `out`, swing, gate length. With `song` it plays the drum rows of the song.
  - **Piano Roll (Studio)**: the full piano-roll editor, patterns, `clk` / `run` / `reset` / `pat`, outputs `freq / gate / vel` ×4 like the classic Piano Roll; with `song` the parameter *channel* picks which channel of the song it edits and plays.
  - **Mixer (Studio)**: 16 strips (inputs `in1…in8`, the others for buses), level / pan / mute / solo, per-strip FX chain, sends between strips (strips 14 / 15 are the reverb and delay buses in the example songs), master FX, `g1…g8` gate inputs, **scenes** (the `scene` input takes a pattern number; the field under a strip lists the numbers where it sounds, `1,3-4`) and a **sleep timer** (minutes, then a fade-out in seconds; `left` shows what remains). With `song` its strips are the song's inserts.
  - **Effects as nodes**: *EQ, Compressor, Filter, Distortion, Bitcrusher, Chorus, Phaser, Delay, Reverb, Pump (sidechain), Trance Gate, Stereo Width* (Audio) — inputs `L` / `R`, outputs `L` / `R`; Delay, Pump and Gate follow `clk` or `bpm`.
  - Presets: *Studio: Drum Machine → Sampler*, *Studio: Playlist → Piano Roll → Synth*, *Studio: Sleep Mixer*, *Studio: Arranged Song (one wire per lane)*, *Studio: Effects Chain*, and eight *Studio Song: …* (techno, trance, deep house, drum & bass, acid, dubstep, lo-fi, ambient) built as Song + blocks + synths + Mixer.
- MIDI keyboard input, ADSR envelope
- **Winamp** (Music; no skins): **Music Player (Winamp)** plays one track — play / pause / stop, seek, volume, balance, speed, elapsed / remaining time, kbps / kHz / mono / stereo, stereo `l` / `r` outputs plus `pos`, `time`, `playing`, `end`, `title`; keys **Z X C V B** while it is focused; the next track is decoded in advance, so tracks follow without a gap. The track list is a separate, reusable node **Playlist** (`modules/playlist.js`): it keeps the list in the patch, with shuffle / repeat off / all / one and drag-to-reorder, and wires to a player — `fs` / `url` / `name` / `go` / `nfs` / `nurl` go to the player, `next` / `prev` / `end` / `req` / `playing` come back. Files live in the shared file storage (the same as **Files** and the Sample Library): **files** puts a copy into *Files → Music* (or into the library as mono clips — the *→ Samples* choice), **library** picks from the file manager, files can be dragged from a Files node onto the playlist or sent by wire (`add` ← Files `send`). URLs and **Internet Radio** stations (`url` + `name` wires, or all found stations from Internet Radio's `stations` output (every station, with or without coordinates) into `rows` with the **stations** button) play as streams through `<audio>`, like Audio Stream. **Media Library** (`modules/medialib.js`, logic in `modules/medialib-kernels.js`, `node tools/test-medialib.mjs`) is the tree of the classic Winamp library: *Local files* (Music — the *Music* folder of Files, Recently added, Artists, Albums, from the ID3 tags) and *Network services → Internet Radio* (stations from the `rows` wire). A click on a category puts its tracks on the `list` output, a double click also pulses `play`; wire `list` → Playlist `set` (replaces the list) and `play` → Playlist `req`. **Graphic Equalizer (10 bands)** (Audio) — Winamp's bands 60 Hz … 16 kHz, preamp, 16 presets, response curve, double click a slider to zero it. Presets *Winamp* (library + player + playlist + equalizer + Radial Spectrum / Spectrum Bars; the ▦ view lays them out like the classic Winamp) and *Winamp: Internet Radio Playlist*. Logic: `modules/player-kernels.js`, `node tools/test-player.mjs`
- **Band FFT (few bins)** (Processing): an FFT that outputs only 4…128 bands (log / mel / linear scale, tilt dB/oct, fall time) as a `spec`; also `bass` / `mid` / `treble` / `level` (0…1), a `beat` pulse and the tempo `bpm` (median of the beat intervals)
- **Visualizers**: **Spectrum Bars** (Analysis; styles bars / round / led / mirror / line, peak markers; takes Band FFT or a plain FFT and groups it into bars itself) and, in Music, **Radial Spectrum** (rotating circle, bass pulse, flash on the beat), **Neon Waveform** (triggered line, ring, XY / Lissajous), **Beat Particles** (burst on the beat, fountain by bands, warp flight) and **Ridgeline Spectrum** (the "Unknown Pleasures" 3D history). Presets in *Music: Visualizers*. Logic: `modules/viz-kernels.js`, `node tools/test-viz.mjs`

### Output & extensibility
- Sound card output (per-node output device selection, peak/clip meter), WAV / MP3 recording (files named by date and time; optionally streamed straight to a disk file, so the length is not limited by memory — Chrome/Edge), log to a [Table](help/data.md#table), trigger recorder (modes manual / **gate** — records while `trig` is high, e.g. the receiver's `sqOpen`, plus *post-record* time after it closes / level / edge; *tag* goes into the clip name)
- Sound card output (per-node output device selection, peak/clip meter), WAV / MP3 recording (files named by date and time), log to a [Table](help/data.md#table), trigger recorder
- **Network Out**: WebSocket (`ws://`, `wss://`, reconnect) — text on change, numbers as a JSON object every period, or mono PCM16 audio (a JSON header first, then binary blocks). Example: `websocat -s 8765` on the receiving side
- **Map** (offline vector base map, OSM / satellite / relief tiles and overlays, GeoJSON / KML / GPX layers, tracks, markers — see [Map and records](help/map.md#map-and-records)), screen transmitter, indicators
- **Beep** (Output): a `go` pulse plays a short tone through its own audio context (independent of the engine; the browser allows sound only after a tap on the page). Pitch (the `freq` input overrides), length, number of tones in a row and the pause between them, volume, wave, *min gap between beeps*; **Test** plays one. Used in the preset *Object Detect: Camera Video and Photo* (a beep on every new object).
- **Vibrate** (Output): a `go` pulse vibrates the phone (Vibration API) for *duration* or the `ms` input; *pattern* (`200 100 200`, ms) makes a series. Android Chrome / Firefox only, the page needs a tap first
- **Notify**: speaks a text aloud (speech synthesis), shows a system notification and/or vibrates — on a new text or a `go` pulse, with a minimum gap between alerts (e.g. a decoded message or a CFAR detection → voice alert)
- **MQTT Out**: publish text or a number (template `{v}` / `{v:N}`) on change; topic from a parameter or a wire, QoS 0/1, retain. Example — an IR blaster on Tasmota: *IR Encode* (output format «tasmota mqtt») → MQTT Out `cmnd/<device>/IRsend`
- **Serial Out (WebSerial)**: write text or a numeric value to a serial port — Arduino, relays, transceiver CAT control (template `FA{v:11};` turns a frequency into a Kenwood command); device replies come back on the `reply` output
- **HTTP Out**: webhook request (POST / PUT / GET, custom headers) — text on change, or numbers as a JSON object on a `go` pulse or every period. The server must allow CORS, and from the https demo only `https://` (or localhost) works
- **MIDI Out** (Web MIDI): `gate` → note on/off, `note` (or `freq` in Hz straight from *MIDI Keyboard*) with velocity, and a `cc` input for control change — drive hardware synths and a DAW from any signal
- **Firmware flashers** (WebSerial, Chrome/Edge): **Flasher: Quansheng UV-K5** **Flasher: Radtel RT-880** and **Flasher: Radtel RT-890** and **Flasher: Radtel RT-4D** — see [Firmware flashers](help/protocols.md#firmware-flashers)
- Module Builder and Script nodes for writing custom DSP code in the browser

## Proxy for KiwiSDR and lists

The **CORS proxy** from the settings panel is used for list downloads (Satellites, Station Schedule, SDR Receivers Directory…) and for the **KiwiSDR** and **OpenWebRX** nodes (OpenWebRX: `http://host:port/ws/`). For Kiwi the address `http://host:port/<ts>/SND` is substituted into the proxy URL the same way (`{url}` is replaced by the encoded address, otherwise the address is appended) and the scheme `http(s)` becomes `ws(s)`, so the proxy must pass WebSocket. Without a proxy the node connects to `ws://host:port` directly, which an https page cannot do (mixed content).

nginx, setting `https://example.com/proxy/` (the address is appended):

```nginx
# http {} block
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

# server {} block
location ~ ^/proxy/(?<sch>https?):/+(?<hst>[^/]+)(?<pth>/.*)?$ {
    resolver 1.1.1.1;
    proxy_pass $sch://$hst$pth$is_args$args;
    proxy_http_version 1.1;
    proxy_set_header Host $hst;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_ssl_server_name on;
    proxy_read_timeout 3600s;
    add_header Access-Control-Allow-Origin * always;
}
```

This is an open proxy to any host: restrict it (`allow`/`deny`, basic auth, or a whitelist of hosts) before exposing it. Lists need the CORS header, Kiwi only the WebSocket upgrade.

Pitfalls:
- The `location` prefix must match the one set in Settings (`/proxy/`, `/p/`…).
- An address with `.php` in the path (e.g. Celestrak `gp.php`) is caught by `location ~ \.php$` if that one comes earlier in the file: among regex locations the first match wins. Put the proxy `location` above it, otherwise you get a 404 without the CORS header.
- `always` in `add_header` is required: without it the header is not added to 4xx/5xx responses, and the browser shows "blocked by CORS policy" instead of the real error.
- Check: `curl -s -D- 'https://example.com/proxy/https://celestrak.org/NORAD/elements/gp.php?GROUP=amateur&FORMAT=tle' | head` — expect `200` and `Access-Control-Allow-Origin: *`.
