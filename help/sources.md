# Sources

Everything that brings a signal or data into the graph.

### Sources

- Oscillator, sweep/jammer, constant, LFO (a `sync` input restarts the phase on a rising edge, the `sync` output pulses at the start of every period — chain it with the oscillator's `sync` or another LFO), text source
- Microphone (stereo A+B), audio file, audio stream URL, tab/screen audio capture
- **Not from this reality** (synthetic, nothing is received): *Strange Attractor* (Lorenz / Rössler / Thomas, three outputs — try the phase scope), *Black Hole Merger* (inspiral chirp → ringdown → silence, with a `sync` pulse), *Pulsar* (period, flicker, missing pulses, scatter tail), *Schumann Resonance* (five Earth–ionosphere modes driven by lightning, a frequency multiplier brings it into the audible range), *Cellular Automaton* (Wolfram rules, rule 30 as a bit generator)
  - These are teaching models, not physics simulations. *Strange Attractor* uses the standard parameters (the largest Lyapunov exponent measured: Lorenz 0.91, Rössler 0.07). *Black Hole Merger* is the Newtonian inspiral chirp (f ∝ (t_c − t)^-3/8, A ∝ f^2/3) with a simple damped ringdown at 1.2 × the merger frequency, the duration is stretched to be audible, the noise is white. *Pulsar* has correlated flicker and a scatter tail (convolution with an exponential), but no dispersion. *Schumann Resonance* has real mode frequencies, the relative amplitudes are set by hand
- **USB SDRs** directly via WebUSB: RTL-SDR, HackRF, Airspy R2/Mini, Airspy HF+, HydraSDR RFOne, SDRplay RSP1 / MSi2500, RX-888 (mkI/mkII/mkIII) — multiple tuners/demodulators per device, wideband sweep with a panoramic waterfall, IQ recording and playback in WAV / SigMF (see [USB SDR](sdr.md#usb-sdr))
- **KiwiSDR** remote receivers (public list included); **SDR Receivers Directory** (Geo) puts public KiwiSDR / SpyServer receivers on the Map — click a point and its host:port goes to the KiwiSDR node (see [KiwiSDR behind HTTPS](#kiwisdr-behind-https))
- **OpenWebRX** / OpenWebRX+ remote receivers: the *OpenWebRX* node connects to `ws://host:port/ws/`, the server demodulates (AM / LSB / USB / CW / NFM / WFM), the node outputs `audio`, `rssi` and `spec` — the server's own band spectrum (FFT frames, float32 or ADPCM) on an absolute frequency axis, so it can go straight to Spectrum Analyzer. Wired the same way as **USB SDR**: `spec` → analyzer `spec`, analyzer `f1` → `tuneFreq`; the analyzer draws the channel curtain (passband, mode, bandwidth) around the tuned frequency, shows the passband under the cursor, and dragging a curtain edge sets `bw` (analog modes). `tuneFreq`, `bw` and `demod` (USB SDR names — USB, LSB, AM, NFM, WFM…) are inputs, `tuneFreq`, `bw`, `freqLo`, `freqHi` outputs; `steerFreq` is accepted and ignored (the server's band is chosen with *profile*) **Profiles** (the server's bands / receivers): the *profile* parameter (or the `profile` input — a name, id or part of a name) switches them; a switch changes the receiver for all listeners of the server, so it is never done on its own — out of the band the status lists the other profiles. **Modes** come from the server (*mode* list, only the ones its features allow); digital modes (FT8, WSPR, JS8, APRS, POCSAG, DMR, YSF, D-STAR, NXDN…) are decoded by the server: the node sets the underlying modulation (*under*, default the server's first) and the secondary mode, decoded messages and metadata go to `rec` (`kind` = `decoded` / `metadata`, `t`, the server's fields) and the last one as a line to `text`; `profile` outputs the current profile name. The delay is set by *audio buffer* (default 300 ms: that much is collected before playback and after an underrun; a backlog above three buffers is dropped) The frequency is absolute (the offset from the server's band centre is computed by the node; outside the band the status says which range the server covers); plain and IMA-ADPCM audio are supported. Same proxy rules as for KiwiSDR. Checked against the protocol of the reference client's sources and a fake server in `tools/test-openwebrx.mjs`, **not against a live server**; profile switching is not used
- Camera, video, image, accelerometer and Generic Sensor API (*Camera*: **find all cameras** lists every video input the browser exposes — extra lenses, IR / night-vision, USB thermal cameras that show up as UVC — and lets you pick one; what the browser does not expose stays invisible)
- **Motion Detect**, **Pulse (camera)**, **Timelapse**, **Color / Spectrometer** (Video): what to do with a camera picture besides looking at it — see [Camera tools](video.md#camera-tools)
- **Barcode / QR** (Video): reads QR codes and barcodes from a camera, video or image frame (BarcodeDetector — Chrome / Android; where the browser has none, QR codes are read by the built-in jsQR, barcodes of other kinds need BarcodeDetector): the text, a pulse on `go`, records `{format, value}`, a repeat of the same code is ignored for a set time
- **Object Detect** (Video, `modules/objdet.js`, logic in `modules/objdet-kernels.js`, `node tools/test-objdet.mjs`): finds objects (80 COCO classes: person, car, dog, cat, phone…) in a photo or video. Inputs: `vid` (live video — Camera, Video) and `img` (photo, IP Camera frames); a photo is detected once (again when a setting changes), video every *detect every* seconds. Outputs: `img` (the frame with boxes; read from the canvas only when something is wired to it), `text` (`#id label 87%` lines), `go` (pulse), `rec` (`{label, score, x, y, w, h[, id]}`, fractions of the frame), `count`, `total`. Parameters: min confidence, only these classes (`person, car`), pause between detections (counted from the end of the previous one, default 0.5 s; nothing runs while the tab is hidden), detection size (the net shrinks the frame to ~300 px anyway; default 320), picture width, advanced *compute* (auto / webgl / cpu: if the browser crashes with SIGILL on a device, try cpu — slower, but it does not touch the GPU driver), **tracking** (greedy IoU matching per class: every object keeps an id, a lost one is remembered for *keep* seconds; with tracking `go`/`rec` fire only for **new** objects, `total` counts them — people counter, door watcher). COCO-SSD on TensorFlow.js; TF.js and the model (about 7 MB) load from jsDelivr and Google storage on the first start, so the first run needs a network. For offline use put `tf.es2017.min.js` (not `tf.min.js`: it needs `unsafe-eval`, which the page CSP forbids), `coco-ssd.min.js` and the `model.json` with its shards into `vendor/` and set the advanced *script URLs* and *model.json URL*. Preset **Object Detect: Camera Video and Photo**. Checked in headless Chromium with the real TF.js and model; not tried on a real camera.
- **QR Code** (Video, `modules/qr.js`, pixels in `modules/qr-kernels.js`, `node tools/test-qr.mjs`): text (the `text` input or the parameter, UTF-8) → a QR picture on `img` (error correction L / M / Q / H, pixels per module). The generator (`vendor/qrcode.min.js`, MIT) and the reader (`vendor/jsqr.min.js`, Apache-2.0, licences in `vendor/qr-LICENSE`) load on first use and work offline. Sync devices has **Show QR** (the pair key as a link) and **Scan QR** (camera, the key is taken from the link or from plain text), so a key no longer has to be typed or sent. Preset **QR: Generator and Reader Loop (no hardware)**.
- **WebSerial on Android**: Chrome for Android has no `navigator.serial`, so `modules/webusb-serial.js` provides it over WebUSB (OTG cable): CDC-ACM (tinySA, Flipper, Pico, native-USB ESP32), CH340/CH341 and CP210x adapters — and the same shim works **inside the DSP app** (its `usb-bridge.js` gives the WebView a full WebUSB, so Serial Port works there over OTG too). Not tried on real hardware
- **tinySA / tinySA Ultra** spectrum analyzer over WebSerial: sweep into the spectrum/waterfall, screenshots, signal generator (see [tinySA](sdr.md#tinysa))
- **ESP-SDR (ESP32)** over WebSerial: raw I/Q bursts from an ESP32's built-in radio ([ESPARGOS/esp-sdr](https://github.com/ESPARGOS/esp-sdr) firmware), spectrum in the browser (see [ESP-SDR](sdr.md#esp-sdr))
- **Command Templates** (Control, `modules/flow.js`, logic in `modules/flow-kernels.js`, `node tools/test-flow.mjs`): text commands with parameters for Serial Port, Text over Network, BLE UART, MQTT Out… One template per line — `TUNE {f}`, `MODE {m}` — each `{name}` becomes an input pin of the same name (wire a knob, Cases, a number from anywhere in the graph), and every line gets a **▶ button** in the node plus a `g1…` input (a 0→1 pulse sends it). Firing builds the line — values substitute into the placeholders (integers without a dot, floats trimmed) — and it comes out on `text` (Serial Port's text input sends every change), with `go` (a pulse in the same block) and `rec` (`{cmd, text}`) alongside; a placeholder without a wired input stays visible as `{f}` in the output. Preset *Serial: Command Templates (Parameters → Serial Port)*
- Serial port (WebSerial): reads lines from the device and now sends text to it too — a `text` wire or the Send field (each line goes with `\n`; `\\n`, `\\t`, `\\xHH` escapes), e.g. commands to firmwares like [`tools/radio-bridge-esp32c5`](../tools/radio-bridge-esp32c5/radio-bridge-esp32c5.ino) (ESP32-C5 Wi-Fi/BLE/Zigbee USB bridge: `MODE WIFI|BLE|ZB`, `CH`, `TX …`); a Zigbee temperature/humidity sensor network reports straight into records through [`tools/zb-coordinator-esp32c5`](../tools/zb-coordinator-esp32c5/zb-coordinator-esp32c5.ino) (ESP32-C5 as Zigbee coordinator: sensors join while the network is open, every measurement comes as a JSON line `{"zb":"temp","addr":"0x1234","ep":1,"v":23.45}` — Table, Rule, dashboard; `OPEN s`, `REPORT min max delta`, `POLL`), **Table** (one node for lists, band plans, bookmarks, logs and the data sequencer: CSV / TSV / JSON / TXT / KML / GPX / GeoJSON, folders in the browser DB; the rows are played one by one by [Row Player](data.md#row-player)), Trigger Clock, Time Base — see [Table](data.md#table)
- **Bluetooth LE** (Web Bluetooth): **BLE UART** (Nordic UART, HM-10 / FFE0 or your own UUIDs — a serial terminal without a cable), **BLE GATT** (any characteristic: notifications or periodic read, write; formats — heart rate, battery, temperature, uint / int / float, hex), **BLE Advertisements** (RSSI, TX power and manufacturer data of one device without connecting — proximity, finding a beacon) — see [Bluetooth LE](phone.md#bluetooth-le)
- **IQ over Network**: a remote SDR as an `iq` source — **rtl_tcp** through a TCP → WebSocket bridge (header, rate, tuning, gain, ppm, bias-T, direct sampling are sent as rtl_tcp commands; a wire on the frequency retunes) or a **raw stream** (uint8 / int8 / int16 / float32, rate and center set by hand) from any program that writes IQ to a pipe, or **SpyServer** through the same bridge — see [Remote SDR](sdr.md#remote-sdr)
- **WebRTC Data**: a direct browser-to-browser channel (RTCDataChannel) with no server — the connection code (offer / answer) is passed by hand, through a messenger or the clipboard: *Create offer* on one side, *Accept offer* on the other, *Apply answer* back. Then text goes like **Text over Network** (lines, JSON into records) and the `send` input writes to the other side. Same network needs no STUN, over the internet set a STUN server. **WebRTC Tunnel** (Control) rides the same connection's `link` output and carries any `rec` records across it unchanged, encrypted by WebRTC itself (DTLS) — whatever a node on one side feeds it (Phone sensors, Network (DSP app) socket events, BLE/GATT, MQTT…), the matching node on the other side gets verbatim, so two DSP instances (e.g. two phones) can trade any graph protocol over one encrypted P2P link; several tunnels share a connection by giving each a different *channel name*. Preset *WebRTC Tunnel: Any Protocol Between Two Phones*
- **Gamepad** (Gamepad API): a gamepad, joystick, steering wheel or pedals as numbers — axes `a1…` (with a dead zone) and buttons `b1…` (analog triggers 0…1), the counts are parameters, the device is chosen by index or the first connected one; the `rumble` / `weak` inputs vibrate it. The browser shows the device only after a button is pressed on it
- **Joystick** (Sources): two sticks and eight buttons on the screen and on the keyboard — click the pad, then **W A S D** is the left stick, the **arrows** the right one, **Space, Enter, Z, X, Q, E, R, F** are buttons `b1…b8`; on a phone drag the sticks with your fingers (multi-touch) and press the buttons. Outputs: `x1 y1 x2 y2` (−1…1, with a dead zone and expo), `b1…b8`, `rec` and a ready **frame** as `text` by a template: `{x1}` −1…1, `{X1}` −100…100, `{r1}…{r4}` 1000…2000 µs (servos / RC), `{b1}…{b8}`, `{bits}`, `{hex}` (a 7-byte frame: `A5`, x1, y1, x2, y2 as signed bytes, buttons, XOR), `{n}` frame counter, `{t}` ms — wire it to *Serial Out*, *BLE UART*, *MQTT Out*, *Text over Network* or *nRF24* to drive a robot, a flight controller, a relay board or your own receiver. Frames go at *frames per second* while a key is held and once more as zeros on release (*keep-alive* repeats them at rest, a counter in the template lets the receiver notice a lost link). *hold*: a stick Y that keeps its value like a throttle. **Esc** is an emergency stop (all zeros until *Resume*). *invert vertical* turns the Y of the right, the left or both sticks over (for pitch: the down arrow / pulling back is up; the pad shows the result). The keyboard works while the pad is focused or always (not while typing in a field). A wire on `ex1…ey2` (for example from *Gamepad*) takes over that axis. Check a real machine without propellers first. Logic: `modules/control-kernels.js`, `node tools/test-control.mjs`
- **nRF24L01+** (Sources, over a USB bridge): an nRF24L01+ radio module on an Arduino Nano / Uno (or any board with the RF24 library) running [`tools/nrf24-bridge`](../tools/nrf24-bridge/nrf24-bridge.ino) — the page talks to it over WebSerial (Chrome / Edge, 115200) with lines `CFG / TX / RXON / SCAN`. **Transmit**: text or hex from `send` goes out on the chosen channel (2400 + ch MHz), rate (250K / 1M / 2M), address (3–5 bytes), payload size (a fixed one pads the frame, 0 is dynamic), power, CRC and auto-acknowledge; `ok` shows whether the receiver answered. **Receive**: every packet as `rx` (text), `hex`, a pulse on `go` and a `rec` (channel, address, length, hex, text). **Scan**: the bridge listens for a carrier on all 126 channels several times and the share of hits comes out as `spec` (2400…2525 MHz) for the Spectrum Analyzer — to pick a channel clear of Wi-Fi. A wire on `ch` retunes. It talks to your own devices on your own channel and address and does not sniff other people's traffic. The firmware and the parser are checked against the protocol only (`node tools/test-control.mjs`, a simulated bridge in the browser), not on real hardware yet. nRF52 / nRF Connect boards over BLE: *BLE UART* (Nordic UART) and *BLE GATT*. Presets *Joystick: Keyboard and Screen Sticks → Serial*, *Joystick: Gamepad → Frame → MQTT*, *nRF24: Joystick → Radio Link*, *nRF24: Receive Frames*, *nRF24: 2.4 GHz Channel Scan*
- **Flight Sim** (Sources): an arcade aircraft on the *Joystick* or a gamepad, or a camera on an ADS-B aircraft; cameras chase / cockpit / tower / orbit for *Video Overlay* over *Horizon* terrain that is downloaded once and kept offline — see the node reference
- **HID Device** (WebHID): any USB / Bluetooth HID device without a driver — foot pedals, remote controls, USB scales and sensors, barcode scanners, your own boards (Leonardo / Pro Micro, RP2040). Input reports as hex and as records, one field of the report as a number (offset, format, bit, scale, report id filter), the `send` input writes output or feature reports. Keyboards and mice are closed to WebHID by the browser
- **FUNcube Dongle Pro+** (WebHID, `04d8:fb31`): tuner control — frequency (with ppm correction), LNA, mixer gain, IF gain 0–59 dB, bias-T, RF / IF filters; outputs `fc` for the `fc` input of **I/Q → IQ**. The IQ itself comes as USB audio: **Microphone** in *stereo device* mode at 192000 Hz, then **I/Q → IQ** (preset *FUNcube Dongle Pro+: Receiver*). The original FUNcube Dongle Pro (`fb56`) has a different command set and is not supported
- **Speech to Text** (Web Speech API — Chrome / Edge / Safari, the browser's own recognizer, listens to the default microphone, not a graph signal): every phrase as `text` and as a `rec` `{text, conf, lang}`, a pulse on `go`, interim text in the readout, language by a code (`ru-RU`)
- **NFC** (Web NFC, Chrome on Android over https): read NDEF tags — serial number, the first text / URL / JSON record as text, every record as a `rec`; write text, a URL or JSON to a tag (the *Write* button, a pulse on `go`, or a text on the `write` input)
- **MQTT In** (over WebSocket, QoS 0/1, username/password, auto-reconnect): subscribe to topic filters (`+` / `#`); a message comes out as text, topic, a number (the payload itself, or a JSON field — `temp.value`) and as records (a JSON object or array becomes `rec` with the topic added, so Tasmota / ESPHome / Home Assistant sensors with lat / lon go straight to the map). The browser cannot open `mqtt://` itself: give the broker a WebSocket listener (Mosquitto `listener 9001` + `protocol websockets`, EMQX, HiveMQ, the Home Assistant add-on); from the https page only `wss://` works — see [MQTT](protocols.md#mqtt)
- **Messenger** (Sources; `modules/msgr.js`, protocols `modules/msgr-kernels.js` + `msgr-session.js`, `node tools/test-msgr.mjs`, `node tools/test-msgr-net.mjs`): one node for thirteen ways to talk and to read — **Nostr** (public relays `wss://…`, the channel is a hashtag; events are signed with BIP-340 Schnorr, `nsec` / hex key or a new anonymous key per session, incoming signatures are verified), **ntfy** (topic over HTTP, token or user:password), **Matrix** (homeserver, password or access token, a room id or alias, joins it itself), **Telegram** (a bot from @BotFather: long poll, replies go to the last chat or a fixed one), **IRC** (`wss://` straight from the page, or `ircs://host:6697` through the Node bridge), **XMPP** (account `user@domain`, STARTTLS + SASL PLAIN, MUC room; a password is never sent without TLS unless *plain* is ticked; needs TCP — see below) and **APRS-IS** (needs TCP: *user* is the callsign, *channel* the server filter — `r/lat/lon/km`, `m/km`, `b/CALL*`, default messages to you; stations come out as records with `lat` / `lon` — wire `rec` to *Map*; messages are written `@CALL text`, acknowledged and retried like on air; with no passcode it is receive-only — the passcode of a callsign is entered by its licensed owner, it is never computed for you) and **Email** (needs TCP: *server* `imaps://host:993` — new mail in the mailbox *channel* comes out as `[subject] text` (MIME, base64 / quoted-printable, charsets, RFC 2047 names), read with `BODY.PEEK` so nothing is marked as seen; *smtp* `smtps://host:465` or `smtp://host:587` with STARTTLS — a letter is written `@name@host subject⏎text`; the mailbox is polled every *poll* seconds; the password is never sent without TLS) and **SMS** (the phone's own text messages through the DSP app for Android — no Node bridge: the page of the app connects to the phone's socket, `server` empty = `ws://127.0.0.1:8765`; incoming SMS come out as `from number: text`, a message is written `@+79001234567 text` and goes out as an SMS from the phone (the app asks for the SMS permission and sends at most 5 a minute); only the page of the app has the key, other sites get `forbidden`) and **Reticulum / LXMF** (`modules/rns-kernels.js`, `node tools/test-rns.mjs`; the encrypted mesh that Sideband and NomadNet use: *server* `rns://host:port` — the TCP server interface of any Reticulum node, needs TCP like IRC; the node makes its own identity — 128 hex digits kept in the *password* field, it is your address and your private key —, announces `lxmf.delivery`, hears the announces of others (signature and destination hash checked), receives messages in one packet or over a Link, as Sideband sends them (the signature is verified against the announced key, delivery is confirmed) and sends them in one packet (a longer text goes in pieces of ≤ 240 bytes), with delivery proofs; write `@name text` (a name heard in announces) or `@<32-digit address> text`, *channel* is the default recipient; needs X25519 and Ed25519 in Web Crypto — Chrome 137+, Firefox 130+, Safari 17+. Not supported: Resource (long messages, attachments), propagation nodes, stamps. Checked against the reference RNS / LXMF: a real `rnsd` and a Python LXMF peer behind it, `RNS_PY=… node tools/test-rns.mjs`), and the public feeds **Mastodon** and **Bluesky** (`modules/feed-kernels.js`, `node tools/test-feed.mjs`; read-only, polled every *poll* seconds; no TCP and no login where the service allows it): *channel* says what to read — `#sdr #radio` (any of the tags), `-#spam` drops posts with a tag, `@account` and a feed link / `at://` feed (Bluesky), `local` / `home` (Mastodon; empty — the public timeline). **Mastodon** reads `/api/v1/timelines/tag/…` of the instance in *server* (empty — mastodon.social) **without an account** when the instance lets anonymous callers see timelines (the admin's setting; mastodon.social does) — otherwise put an access token with the `read` scope into *password*; the catch-up after a pause goes page by page with `since_id` / `max_id`. **Bluesky** reads accounts and feeds anonymously from `public.api.bsky.app`; the **search by `#tag` is closed to anonymous callers** (HTTP 403), so for tags enter your handle in *user* and an **app password** in *password* (the node logs in at bsky.social and renews the token itself). Every post is a record `{id, from, name, text, url, tags, lang, avatar, image, likes, boosts, replies, cw, boost_by, t}` — wire `rec` to a **Table**: a list `feeds/radio` in the browser database keeps it (key `id` — a post seen twice is one row, *max rows*, *newest first*, cards), survives a reload, is backed up and synced; filter it there (`tags:antenna`, `lang:ru`, `likes>10`). *also fetch…* sets how far back the first read goes (0 — only what comes later); **RSS / Atom / JSON Feed** (*server* — feed addresses, several separated by a space; *channel* — words: any of them in the title, text or categories, `-word` drops an item; polled every *poll* seconds, at least 60; RSS 2.0, Atom, RSS 1.0 / RDF and JSON Feed are read, a truncated or sloppy feed as far as it goes, DTD entities are never expanded; the record adds `title`, `summary`, `feed` — a headline is the `text` for Chat). **A browser cannot read most feeds (no CORS headers)**: set the *TCP gateway* to a **Node bridge** — it fetches the feeds itself (`--hosts` limits which servers), or tick *through the CORS proxy* (Settings; the bridge is one too, see *CORS proxy of the Node bridge* and *Devices*), the Android app needs nothing. **Where TCP comes from** (IRC `ircs://`, XMPP, APRS-IS, email — a browser cannot open sockets): inside the DSP app for Android the phone itself (`tcp.connect` with `tls` / `starttls`, certificates checked by Android's store; *via* `auto`); from any other page — one *bridge* address (the «TCP gateway»), which is either the DSP app of a phone (`ws://192.168.0.5:8765`; tick *Let any page use actions* in the app Settings) or the Node bridge (`ws://127.0.0.1:8777`) — the node tells them apart by the greeting. Inputs `send` (a message) and `to` (a recipient/chat; empty — the channel), outputs `rec` (`{t, proto, dir, from, to, text}` — wire to *Chat*, its «my name» = the node's nick), `text`, `from`, `new`, `ok`. Your own messages come back as outgoing (by the server where it echoes them, locally where not). *history* also fetches the last N seconds, *reconnect* retries with a pause, *via* picks where the protocol runs (auto: in the page, through the bridge only where a TCP socket is needed). The presets *Messenger: One Chat for Nostr, ntfy, Matrix, Telegram, IRC and XMPP* and *APRS-IS: Messages and Stations on the Map* and *Email: Mailbox as a Chat (IMAP / SMTP)* and *SMS: Texts as a Chat (DSP app on Android)* *Reticulum: LXMF Messages over a Mesh (Sideband / NomadNet compatible)* and *Feed: Mastodon and Bluesky by Tags into a Table (cards)* and *Feed: RSS / Atom News by Keywords into a Table (cards)* show it.
- **Node tools** (`tools/node`, Node 22+, no dependencies; the same protocol code as the page, loaded through `vm`): `bridge.mjs` — a WebSocket bridge for the page (`node tools/node/bridge.mjs [--token T] [--hosts irc.libera.chat,*.example.org]`, default `ws://127.0.0.1:8777`; opens TCP/TLS for IRC, XMPP, APRS-IS, email and Reticulum and can run any other channel on the server side; Origin and token are checked, `--hosts` limits the servers it may reach); `msgr.mjs chat <proto> …` — a chat in the terminal (incoming to stdout, stdin lines go out); `msgr.mjs relay links.json` — forwards messages between channels of any protocols (`[{"proto":"irc",…},{"proto":"nostr",…}]`, a message arrives as `[nick] text`, own messages are not re-sent — no loops). A bridge between two channels keeps working with no browser open, e.g. on a Raspberry Pi.
- **CORS proxy of the Node bridge** (`node tools/test-proxy.mjs`): the same bridge answers `GET /proxy?token=…&url=<address>` — so **one line in Settings → CORS proxy**, `http://127.0.0.1:8777/proxy?token=TOKEN&url={url}` (or `http://<device>:8777/…` for a bridge on another machine), gives every module that has a *through the CORS proxy* tick (IP Camera, IPTV, Stream Check, Internet Radio, Packet Link, RSS…) and every module that always uses the proxy (satellites, terrain, schedules…) a proxy of your own instead of a third-party service that would see every address you open. GET and HEAD, `Range`, redirects (each hop is checked again), and **streams are passed on as they come** (MJPEG, HLS, radio — closing the page closes the target). The page gets CORS and Private Network Access headers, also on errors, so a refusal can be read. Protection: the page's *Origin* and the token are checked (`--origin`, `--token`), `--hosts` limits the targets, and by default the bridge refuses loopback, link-local (cloud metadata `169.254.169.254`), unspecified and multicast addresses — checked on the address actually connected, so a name that resolves to one is refused too, and after every redirect; the local network (cameras) is allowed, `--proxy-no-private` closes it, `--proxy-loopback` opens loopback (e.g. a camera server on the bridge machine), `--no-proxy` turns the endpoint off. The page's cookies and authorization are not passed to the target, its cookies are not passed back. An `http://` bridge on another machine is mixed content for an `https://` page: allow it in the browser or serve the bridge over https.
- **Certificates, `wss://` and `https://`** (`modules/cert-kernels.js`, `tools/node/tlsdir.mjs`, `node tools/test-cert.mjs`, `node tools/test-bridge-tls.mjs`): a page on `https://` opens `ws://` only when the browser is told to allow insecure content; `wss://` needs a certificate the browser trusts. Two ways to get one, both with **your own CA** (no third party, works for names and IPs of your local network): (1) the Node bridge does it itself — `node tools/node/bridge.mjs --tls` makes a CA and a certificate in `~/.dsp-bridge` (`--tls-dir`), for its host name `.local`, `localhost`, `127.0.0.1`, `::1` and the LAN addresses (`--tls-name pi.lan --tls-name 10.0.0.7` adds more), renews it when the addresses change or a month is left, serves **`ws://` and `wss://` (and `http://` / `https://`) on the same port** and the CA at `http://<address>:8777/ca.crt` (public, never a key); it prints the CA SHA-256 fingerprint to compare when you install the CA; `--cert FILE --key FILE` uses your own files (mkcert, Let's Encrypt) instead; (2) **Settings → Devices → Certificates** makes them in the browser: type the names and IPs of a server, press *Create certificate* and get `<name>.crt` (with the CA chain), `<name>.key` and `dsp-ca.crt` for any server that speaks TLS; the CA is made once and kept in the browser — its private key sits in IndexedDB as a **non-extractable key** (page code can sign with it, nobody can read it out), *Forget this CA* removes it. **Trust the CA once** on each device that opens the page (Chrome / Edge: Settings → Privacy and security → Security → Manage certificates → Authorities → Import; Android: Settings → Security → Install a certificate → CA certificate; iOS: install the profile, then Certificate Trust Settings; desktop OS: the keychain / certificate manager) — after that a `wss://pi.lan:8777` device from the list works without *allow insecure content*. **The CA is limited by name constraints** to `localhost`, `.local`, `.lan`, `.home.arpa`, `.internal` and private / loopback / link-local networks, so even a leaked CA key cannot vouch for a public site (OpenSSL and the browsers enforce it; checked with `openssl verify` and real TLS handshakes). Certificates are ECDSA P-256 / SHA-256, a year long, the CA ten. **The Android app can speak `wss://` too**: the phone makes its own key and keeps it (it never leaves the phone); *Settings → Devices → Certificates → Install on the device* takes a device of the list, asks the app for its public key (`tls.csr`), signs a certificate for it with your CA (the names / IPs of the field, or the address of the device) and sends back only the certificate (`tls.install`) — then `wss://<phone>:8766` opens (the plain `ws://…:8765` keeps working; *Test* shows the TLS port), *Remove from it* wipes the key and the certificate. A certificate for a key other than the phone's is refused by the app. An *unconstrained* CA (for decrypting the traffic of your own device in the VPN mode) is supported by the generator (`certNewCA({constrain:false})`) but is not offered in the UI yet.
- **Proxy mode** (Settings → *Proxy mode*, next to *CORS proxy*): **always** — everything that uses the proxy goes through it (the old behaviour, and the default); **on error** — directly first, and only when the browser refuses a request to another site (CORS, or an `http://` address from an `https://` page) the same GET / HEAD is repeated once through the proxy; a host the proxy helped is remembered for the session and goes through it at once — so a proxy that sees your addresses is used only where it is needed (and if the proxy fails too, the original error is shown, not the proxy's); **off** — the proxy field is ignored. Works for every module that calls `fetch`, with no change in the modules. POST, the site's own address and sockets are never repeated; the WebSocket-through-proxy cases (OpenWebRX, KiwiSDR) and nodes that ask for the proxy explicitly keep using it directly. In the Android app the row is hidden (the app handles CORS itself).
- **Devices** (Settings → *Devices*; `modules/gateways.js`, `gateways-kernels.js`, `node tools/test-gateways.mjs`): a list of the bridges you use — a phone with the DSP app, a Raspberry Pi or a PC with the Node bridge, Termux — each with a **name**, an **address** and a **token**. A node takes `@name` in its address field instead of `ws://192.168.0.101:8765/?token=…` (Phone Actions, Phone Link, bitchat, GATT, Net Link, VPN Monitor, Termux, Network Out / Text, Packet Link, IQ over network, Messenger's *TCP gateway* and the SMS server; the address parameter of these nodes is a **list of your devices** (`@phone  192.168.0.101:8765` …) with *custom address…* at the end for any other address; a name that is not in Settings → Devices on this browser is marked, and the list in an open node follows what you change in Settings), and the same name works in **Settings → CORS proxy** (`@lab` = the CORS proxy of that Node bridge: `http://host:8777/proxy?token=…&url={url}`). Every node can use a different device, so one patch can talk to a phone, a Pi and a PC at once; to move a patch to another phone change one address in the list, not in every node. **Test** connects, reads the greeting and says what answered (DSP app / Node bridge / Termux bridge) — a wrong address, port, token or Origin shows at once. **Tokens stay in this browser**: a separate key, never in a patch, a shared patch link, a Table or a backup (*Export…* leaves it out like the sync key; after a restore the names and addresses are back and the tokens are typed again). - **Scans with the screen locked**: records of Wi-Fi, BLE, Bluetooth and cells get the phone's position from the last GPS fix; it used to be taken only if the fix was younger than 30 s, so when the GPS slowed down on a locked screen the records lost the position and filters such as «has lat» dropped them silently. - **Source Locator: levels, bearings and distances** (`use: auto` takes whatever the records carry): besides signal levels (path loss, the unknown power is fitted) and bearings, a record may carry a **distance** — fields `dist` (m) and `distSigma` (m): **Wi-Fi RTT** (802.11mc, the Network node's `wifi rtt`; the app now gives these records the position and the same `dev` key as the Wi-Fi scan, so they join the AP's other marks) and the **Timing Advance** of the serving LTE / GSM cell (a ring at 78 m / 553 m steps: `termuxTaDist`). A BLE advertisement with its **TX power** (`txp`) gives the level at 1 m (≈ txp − 41 dB), so the power is not fitted and even two level marks are enough (`useTx`, on by default). Distances fix the position much better than levels: in the synthetic tests four ranges of ±5 m find the source within 15 m. `use: range` takes only distances; `sigmaDist` is the error when a record has no `distSigma`. The Locate preset now uses `auto` and has a Network node with Wi-Fi RTT at the bottom.

The node outputs one `rec` per hop `{src:'trace', ev:'hop', host, hop, ip, ms, ok, final, round, prev, gap}` as they arrive (`prev` is the previous router that answered, the first one comes from `Phone`; `gap` counts silent hops skipped) and, after every round, one `{ev:'stat', id:'host#hop', hop, ip, sent, recv, loss, last, avg, best, worst}` per hop — a Table with key `id` is a live **mtr**. `rounds` 1 is a plain traceroute, more is mtr; `text` is the table as text, `hops` the count. **Rec → Entities** template «Traceroute (path to a host)» draws Phone → routers → the target (red diamond) with the time on every link; a Graph with layout `LR` turns it into a left-to-right path.
