# Protocols and firmware

MQTT, bytes and files, firmware flashers, Packet Link, HEX Structure.

## MQTT

**MQTT In** and **MQTT Out** (MQTT 3.1.1 over WebSocket, written from scratch, no libraries) connect the workbench to any IoT stack. Each node keeps its own connection; `Connect` / `Disconnect` buttons, auto-reconnect every 3 s, a refused login (wrong user or password) is shown and not retried.

- **MQTT In**: `topic` takes several filters separated by spaces or commas. Outputs: `text` and `topic` (one message per block, a burst is queued), `value` (the payload as a number, or the JSON field named in *JSON field* — `a.b.c`; the last value is kept), `rec` (every message of the block: a JSON object or array → records with `topic` and `t` added; plain text or a number → `{topic, text}` / `{topic, value}`), `new` (a pulse per message).
- **MQTT Out**: `text` is published when it changes (empty text is skipped), `value` when it changes, through the template; the `topic` wire overrides the topic parameter; `ok` is 1 while connected. QoS 1 messages are acknowledged but not re-sent.
- Passwords are stored in the patch as plain text — do not share patches with real credentials.

Presets: *MQTT: Subscribe and Publish*, *IR: Tasmota Blaster over MQTT* (send with *IR Encode*, receive Tasmota `IrReceived.RawData` — *IR Decode* reads that JSON and the `38000,9000,…` body of `IRsend` directly).

## Bytes and files

The `bin` port (brown pin) carries plain bytes: `{d: Uint8Array, name, mime, id}`. A new `id` means new data; nodes compare it to skip repeats. Text ports cannot carry arbitrary bytes, `bin` can.

- **File → Bytes** (Sources): choose a file, it goes out on `bin` when chosen (*send when a file is chosen*), on `go`, on **Send**, or every *repeat* seconds. Outputs `size`, `name`, `new`.
- **Bytes → File** is now the `bin` and `path` inputs of **Files**: the received data is kept in the file store (Files › Received, or the path), optionally also downloaded; the name comes from the data or the path.
- **Bytes → Image** (Decoders): `bin` → `img` (+ `new`, `w`, `h`, `fps`). The format is found by its signature. *mode*: `file` — every `bin` is one picture; `stream` — JPEG frames are cut out of a byte stream by the JPEG structure (an EXIF thumbnail does not break a frame, garbage between frames and a torn frame are skipped and counted), for MJPEG, ESP32-CAM and cameras that write JPEG to a UART; `raw` — pixels without a header: `gray8`, `rgb565` (little-endian) or `rgb888`, width and height set by hand, frames follow each other with no sync (a lost byte shifts the picture — **Reset**). The decoder is asynchronous: while it is busy only the newest frame is kept, the rest is counted as skipped. An animated GIF / WebP gives its first frame (no animation yet), video codecs are not covered. Wire: **Serial Port** → `bin` → **Bytes → Image** → **Frame**; preset *Bytes: Serial Stream → Picture (JPEG / MJPEG / raw)*.
- **Bytes → Text** / **Text → Bytes** (Data): hex, base64, base64url, UTF-8 or Latin-1. Use them to push bytes through anything that moves lines of text.
- **Text: Wrap (prefix/suffix bytes)** (Data): adds arbitrary bytes before and after a text or bytes input. The prefix and suffix are written as a JS string: `\x02`, `\xFF`, `Ж`, `\u{1F600}`, `\r`, `\n`, `\t`, `\0`, `\\`; other characters are UTF-8. Outputs both bytes and text, so no Module Builder is needed.
- **Bytes → Frames** (Protocols) and **Frames → Bytes** (Decoders): for channels that lose, double, reorder or cut data. The file is split into frames `D5 7A | type | xid | seq | total | len | body | CRC-32` (little-endian; the CRC covers type … body). The first frame (META) carries the size, the CRC-32 of the whole file, the name and the MIME type; the rest are DATA frames of *payload per frame* bytes. A frame is one `bin` and one text line (base64 or hex; the receiver tells them apart by the first characters). The receiver accepts frames in any order and any number of times, drops damaged ones, assembles several transfers at once (by `xid`) and checks the size and the file CRC. It reads a stream with arbitrary chunk boundaries and garbage between frames (it looks for the next `D5 7A`), so a raw UART or BLE link works without line breaks. *Carousel* repeats the whole transfer, so a listener that joined late or lost frames gets the rest on the next round — a one-way link needs nothing else. There is no acknowledgement or retransmission request; one frame goes out per engine tick at most (up to the *frames per second* set, which is limited by the tick rate: about 90 at 48 kHz / 512).
- **Transports**: **Serial Port** (`send` in, `bin` out: raw bytes of the port), **Serial Out** (`bin` in), **Text over Network** (WebSocket: `sendBin` in, `bin` out with *binary messages go to the bin output* on), **MQTT In / Out** (the payload as bytes, the topic goes to `name`), **BLE UART** (`bin` in and out; set *bytes per write* to the MTU for speed). For anything else — a sound modem such as TBSK, a radio, a pipe — take the text output of **Bytes → Frames** or the bytes of **Bytes → Text**.
- Preset **Bytes: File over Any Text Channel (Loopback)**. Logic: `modules/bytes-kernels.js`, `node tools/test-bytes.mjs` (CRC check value, image signatures, MJPEG cutting in odd chunks, torn frames, raw pixel formats, loss, reorder, duplicates, damaged frames, garbage, two transfers at once, empty file). Checked in headless Chromium through File → Bytes → Frames → Frames → Bytes → File, over the `bin` wire and over the text wire; WebSerial, WebSocket, MQTT and BLE were not tried on real devices.

## Firmware flashers

Flasher nodes (Output) write a firmware file to a radio in bootloader mode over a serial port (WebSerial, Chrome/Edge). Common to all of them: the firmware comes from the node's own file field or from a `bin` wire (*File → Bytes*); **Port…** picks the port (the browser asks once and the node remembers it), **Flash** opens it and runs the protocol, **Abort** stops at the next step; a rising edge on `go` also starts flashing. Outputs: `progress` (0…1), `busy`, `ok` (pulse), `status`. Hardware not tried: the protocols are ported from [fagci/k1-fw](https://github.com/fagci/k1-fw) and [fagci/rt880-fw](https://github.com/fagci/rt880-fw) and [JuantAldea/RT-890-python-flasher](https://github.com/JuantAldea/RT-890-python-flasher) and [fagci/rt4d-goflasher](https://github.com/fagci/rt4d-goflasher) and checked by `node tools/test-uvk5.mjs`, `node tools/test-rt880.mjs` and `node tools/test-rtboot.mjs` against simulated radios (frames, checksums, retries, lost acknowledgements, NAKs, errors).

- **Flasher: Quansheng UV-K5** (38400 baud): power the radio on with PTT held, press **Flash**. The node waits for five bootloader beacons, answers with the bootloader version and sends 256-byte pages (up to 120 KiB, a `.bin`), each acknowledged by the radio; a lost or refused page is resent up to 3 times. Frames: `AB CD | len | data | CRC-16/XMODEM | DC BA`, data and CRC XORed with a 16-byte table. Logic: `modules/uvk5-kernels.js`, the shared node and port code: `modules/flasher.js`
- **Flasher: Radtel RT-880** (115200 baud): put the radio into the bootloader, press **Flash**. The firmware is a `.bin` or an Intel HEX file (*format → auto* takes HEX if the file starts with «:»; addresses are counted from `0x08002800`, the window is 246 KiB, empty space is `0xFF`, records outside it are skipped, checksums are verified). The node sends `connect` ×3 and `update`, then 246 blocks of 1 KiB (`W | addr | data | checksum`), each acknowledged (ACK 6, NAK 255 — the block is resent up to 3 times), then `end`. If the radio reboots without acknowledging the last block, `end` is still sent and the status says so. *iRadio variant* switches the commands and the checksum offset. Logic: `modules/rt880-kernels.js`
- **Flasher: Radtel RT-890** (115200 baud): power the radio on with both side keys held, press **Flash**. The node probes the bootloader (`52 00 00`, answer `FF`), erases (`39 00 00 55`) and writes 128-byte blocks (`57 | addr | data | sum`, up to 0xEC00 bytes, the tail is padded with zeros), each acknowledged by `06`; a refused or lost block is resent up to 3 times. A firmware that does not fill the memory leaves the radio waiting — the status says so. Logic: `modules/rt890-kernels.js` (shared with the RT-4D profile)
- **Flasher: Radtel RT-4D** (115200 baud): same protocol as the RT-890 with other numbers — checksum offset 72, two erase commands (`39 33 05 10`, `39 33 05 55`), 1 KiB blocks over the whole 246 KiB memory (the image is always padded with zeros to the full size; a larger file is refused). Press **Flash** with the radio in the bootloader

## Packet Link

**Packet Link** (Sources) collects packets from a channel and cuts the stream into records: each one has `hex` and `hexSchema`, so it goes straight into **Table**, **HEX Structure** or **PCAP Writer**. The existing byte nodes (Serial Port, BLE UART, MQTT, WebRTC Data, File → Bytes) wire into its `bin` / `text` inputs, so any channel works.

- **Channels** (*channel*): `websocket` (reconnects), `http stream` (SSE, NDJSON, chunked, pcap; *through the CORS proxy from Settings* for hosts without CORS headers), `serial` (WebSerial), `ble uart` (Web Bluetooth: Nordic UART, HM-10; a notification is a packet), `inputs only`. A browser cannot open TCP or UDP: use a bridge below, or an ESP32 / any device with a WebSocket server. A serial port of a router or another computer: `node tools/node/bridge.mjs --serial esp=tcp://router:2000` (see *Node tools* in Sources) and `ws://127.0.0.1:8777/serial/esp`. The `send` (bin) and `sendText` inputs write to the channel.
- **Frame** (how the stream becomes packets): `message` (one message or notification is a packet), `hex lines` (the longest run of hex bytes in a line; the text before it goes to `prefix`; `data: …` of SSE is understood), `json lines` (fields of the object go to the record, a `hex` / `data` / `payload` / `raw` / `frame` field is the packet), `text lines`, `slip`, `kiss` (AX.25 TNC; the port is in `port`), `hdlc` (flag 7E, stuffing 7D), `cobs`, `len8` / `len16be` / `len16le` (a length in front), `pcap` (a pcap stream; the time and the link type come from the stream, so `hexSchema` follows it — pcapng is not read from a stream).
- **Outputs**: `rec` (an array per block: `t`, `src`, `kind`, `n`, `len`, `hex`, `hexSchema`, `time`, `text`), `bin` (the last packet), `count`, `bytes`. *HEX schema* sets `hexSchema` (`auto`, `eth`, `wifi`, …); *source label* sets `src`.
- **Bridges** (run on the machine that sees the traffic):

```
tcpdump -i wlan0 -U -w - | websocat -b -s 8767     # channel websocket, ws://host:8767, frame: pcap
dumpcap -i eth0 -P -w - | websocat -b -s 8767      # the same, pcap (not pcapng) from Wireshark's dumpcap
websocat -b -s 8767 udp-l:0.0.0.0:5000             # a datagram is a packet, frame: message
websockify 8767 192.168.1.20:3333                  # a TCP server of a device; frame by its protocol
```

  From an https page the browser blocks `ws://` to other hosts: use `wss://`, localhost, or a local copy of the page over http.
- Logic: `modules/link-kernels.js`, `node tools/test-link.mjs` (every frame, chunks split anywhere, broken input, pcap with a link type, the record). Checked in headless Chromium: SSE → Table and WebSocket + SLIP.

## HEX Structure

A packet as bytes and as fields. The node (Data) shows a hex dump with the bytes of every field in its own colour, a tree of the fields with offsets and values, and a line with the whole packet as hex.

- **Inputs**: `bin` and `text` (hex, any spacing) — the bytes to show and parse; `rec` — a record is built into a packet (fields not in the record keep their values; lengths and checksums are recalculated); a record with a `hex` field (DMR, ADS-B, Wi-Fi sniffer) is parsed instead (*rec input*: auto / build / parse; the structure is taken from the record's `hexSchema`); `go` sends the current packet again.
- **Outputs**: `bin` / `text` (the packet), `rec` (every field by its name: `payload.payload.dport`, `body.ies[0].data.ssid`; an enum also gives `<field>_name`; `_len`, `_ok`, `_schema`; a field with `"as":"name"` is also given a short name that does not depend on the position — Wi-Fi: `ssid`, `ds_channel`, `beacon_interval`, `reason`, `auth_status`, so a Beacon, a Probe request and a Probe response all give `ssid` for a graph / Table; an enum can depend on another field: `enumBy` + `enums`, Wi-Fi `subtype_name` follows `type`), `ok` (lengths and checksums agree), `len`, `new`. Lists can name their items: `"key":"id", "val":"data", "as":"ie"` gives `ie.ssid`, `ie.channel`, `ie.rsn.pairwise`, `ie.p2p`… instead of `body.ies[3]…` (repeats become `ie.vendor`, `ie.vendor_2`); a structure's `"derive"` adds fields computed by condition — Wi-Fi: `kind`, `bssid`, `src`, `dst`, `net`; 802.15.4: `kind`, `src`, `dst`, `net` (PAN).
- **Edit**: click a field to outline its bytes; click its value to type a new one (a number, `0x…`, an enum name, `192.168.0.1`, a MAC or hex for byte fields) — the packet is rebuilt and the length / checksum fields are recalculated; click a byte and type hex digits to overwrite it, **Delete** removes it, **Insert** adds `00`; the line under the tree takes a whole packet. *fix* recalculates lengths and checksums after a raw edit.
- **Structures** (list *structure*): `eth`, `arp`, `ipv4`, `ipv6`, `udp`, `tcp`, `icmp`, `icmpv6`, `radiotap`, `wifi` (802.11, every management / control / data frame: beacon, probe, (re)association, auth, deauth, action — Wi-Fi Direct (P2P) and ESP-NOW —, block ack, LLC/SNAP → IPv4 / ARP / IPv6 / EAPOL, the protected-data header; information elements by name, WPS and P2P attributes), `ieee802154` (MAC, beacon, commands, Zigbee NWK / APS / ZDP / ZCL, 6LoWPAN dispatch of Thread), `adsb` (112-bit Mode S: identification, position), `adsb-short`, `ais` (types 1–5, 11, 18, 21, 24), `pocsag`, `pocsag-cw`, `acars`, `ble-adv`, `gsm-l2`, `gsm-cbs`, `gsm-cbch-block`, `gsmtap`, `m17-lsf`, `m17-pkt`, `p25-tsbk`, `p25-lc`, `p25-hdu`, `nxdn-l3`, `tetra-sync`, `tetra-sysinfo`, `dmr-lc`, `dmr-csbk`, `dmr-pi`, `dmr-slottype`. Nested structures are chosen by a field value (Ethernet type → IPv4, IPv4 protocol → UDP), so an Ethernet frame opens down to the UDP payload.
- **Network and application protocols** (`modules/hex-proto.js`; test `node tools/test-hexproto.mjs`) — layers chain like in Wireshark: `eth` → `vlan` / `mpls` / `lldp` / `wol` / `pppoe` / `ipv4` / `ipv6` / `arp`; `ipv4` → `tcp` / `udp` / `icmp` / `igmp` / `gre` (→ `eth`); the `udp` and `tcp` payload is picked **by port** (either direction): `dns` (and mDNS, with name compression), `dhcp`, `ntp`, `tftp`, `vxlan`, `coap`, `rip`, `radius`, `sip`; `http` (80, 8080, 8000, 3128…), `tls-record` (443, 8443: handshake, ClientHello with the SNI host, alerts), `mqtt`, `modbus` (Modbus TCP, request / response told apart by the length), `smtp`, `ftp`, `pop3`, `imap`, `irc`, `sip`, `rtsp`, `bgp`. Also standalone: `websocket`, `http2-frame`, `can` (SocketCAN), `lldp`, `rtltcp-header`, `rtltcp-cmd`. Pick one from the list, or leave `auto` and open a frame: the whole chain is parsed, e.g. `payload.payload.data.http.method`.
- **HTTP, SIP, RTSP** (field type `http`): the start line becomes `method`, `target`, `path`, `url`, `version` (or `status`, `reason`), every header `h.<name>` (`h.host`, `h.content-type`), the query string `q.<param>`, a form body `form.<field>`, a JSON body `json.<path>` (`json.user`, `json.items[0].id`), cookies `cookie.<name>`, Basic authorization `user` / `pass`, multipart files `files`, and `body`. Content-Length, chunked bodies and a response up to the end of data are understood; gzip stays as it is (`enc`). Building works from the same names: set `http.method`, `http.path`, `http.h.Host`, `http.body` (or one `http` text) and the packet is rebuilt with Content-Length.
- **Field types for your own protocols**: `varint` (7 bits per byte, little-endian groups — MQTT, protobuf, LEB128), `dname` (a DNS name with labels and compression pointers; the schema needs `"msg":true` so pointers count from the message start), `http` (above), and the key `until` on `str` / `bytes` — read up to a delimiter (`"until":"\\r\\n"`, `"\\0"`, `"\\x20"`; `optional` — to the end if there is none; the delimiter is written again on build). `list` with `count` takes the count from an earlier field (`"count":"qdcount"`).
- **Filtering HTTP**: Packet Analyzer gets `http.method`, `http.path`, `http.uri`, `http.host`, `http.status`, `http.content_type`, `http.h.<header>`, `http.q.<param>`, `http.form.<field>`, `http.json.<path>`, `http.cookie.<name>`, `http.body`, so `http.method == "POST" && http.host contains api && http.json.user == demo` works on captures, on the Network node's records and on the Packet Crafter's output. A message split over several TCP segments is parsed from its first segment only; TLS is not decrypted. Preset: *Packets: HTTP POST — Craft, HEX Structure Layers, Filter*. For packets from a computer without the phone app: `node tools/node/bridge.mjs` is a bridge for the **Network (DSP app)** node (TCP / UDP client and server, hex records), allowed origins only.
- **Auto structure**: the *structure* list starts with `auto` — the structure is chosen by the content (a structure with a `detect` expression whose fields parse cleanly and agree with the length: Ethernet, ARP, IPv4, IPv6, 802.11, ADS-B). **HEX View** (Data) is the same dump without a structure, for any bytes.
- **PCAP Reader** (Data): a `.pcap` / `.pcapng` file on `bin` (File → Bytes) → one record per packet (`hex`, `hexSchema` from the link type, time, number) at *packets per second* or all at once; the `bin` output is the last packet. **PCAP Writer**: records with a `hex` field (Wi-Fi Sniffer, DMR / ADS-B decoders) and `bin` packets → a `.pcap` file for Wireshark (Save, or after every packet) → Bytes → File. Link types: Ethernet, 802.11, radiotap, raw IP.
- **Own structure**: *advanced → own structure* takes JSON; *Copy chosen structure to JSON* gives a starting point. A structure is `{endian, bitorder, fields:[…]}` or `{root, lib:{name:structure}}` for several linked ones.

```json
{ "endian": "be", "fields": [
  {"n":"ver",  "t":"bits", "w":4},
  {"n":"ihl",  "t":"bits", "w":4, "calc":"payload.off/4"},
  {"n":"len",  "t":"u16", "calc":"_len"},
  {"n":"proto","t":"u8", "enum":{"6":"TCP","17":"UDP"}},
  {"n":"csum", "t":"u16", "fmt":"hex", "calc":"inet16", "to":"payload"},
  {"n":"src",  "t":"bytes", "fmt":"ipv4"},
  {"n":"opts", "t":"bytes", "len":"ihl>5 ? (ihl-5)*4 : 0"},
  {"n":"payload","t":"rest", "sub":{"by":"proto","map":{"17":"udp"}}} ] }
```

Field types: `u8…u64`, `i8…i64` (any multiple of 8 bits), `f32`, `f64`, `bits` (`w` bits, signed optional), `bytes` (`len`), `str` (`len`, `enc`), `str6` (6-bit characters: ADS-B / AIS; `cs` charset, `trim`), `rest`, `list` (repeats a `sub` structure or an `item` until the data ends or `count`), `pad`. Options: `endian` (`be` / `le`, per structure or field), `bitorder` of the structure (`msb`: the first bit is the top one; `lsb`: 802.11), `scale` / `prec` / `unit` (show a number multiplied, the value stays an integer), `fmt` (`mac`, `ipv4`, `ipv6`, `plmn`, `m17call`, `hex`, `bin`, `ascii`, `bcd`, `dbm`, `time`), `enum`, `flags` (bit → name), `when` (the field exists only if the expression is true), `sub` (a structure name, an inline structure or `{by, map}`). Expressions (`len`, `count`, `when`, `calc`) use earlier fields: `+ - * / % & | ^ << >> == != < <= > >= && || ! ?:`, `field.$off` / `field.$len` (offset from the start of the structure and length in bytes), `_left` (bytes left while parsing), `_len` (size of the structure). `calc` is a checksum (`xor` puts a mask over it) — `crc8`, `crc16-ccitt`, `crc16-ccitt-false`, `crc16-x25`, `crc16-gsm`, `crc16-kermit`, `crc16-arc`, `crc16-modbus`, `crc24-adsb`, `crc16-m17`, `pocsag-bch`, `parity32`, `crc32`, `crc32c`, `inet16`, `xor8`, `sum8` (`from` / `to` set the range, `over:"all"` zeroes the field and takes the whole structure; `pseudo:{proto:17}` adds the IPv4 / IPv6 pseudo-header from the parent's `src` / `dst` — UDP, TCP, ICMPv6; `zeroFF`, `optional` for UDP's zero checksum) — or an expression that is recalculated on build.

**AIS Decoder** has a `raw` output: every message (not only positions) as a record with the message bits in `hex` and `hexSchema` `ais` — HEX Structure shows MMSI, status, speed, position in degrees, names and destination; a `text` input takes `!AIVDM` / `!AIVDO` sentences (multi-part messages are joined).

**POCSAG decoder** records carry `hex` (the address codeword and the data codewords, BCH and parity rebuilt) and `hexSchema` `pocsag`: HEX Structure shows the address, function and every 32-bit word with BCH(31,21) and parity checked (`pocsag-bch`, `parity32`).

**ACARS decoder** records carry `hex` (the block without parity bits, then the BCS) and `hexSchema` `acars`: mode, registration, ack, label, block id, message number, flight and text. `node tools/test-hexdec.mjs` runs the decoders' records against the structures.

**BLE Advertisements** records carry `hex` and `hexSchema` `ble-adv`: Web Bluetooth gives no raw packet, so the AD structures (name, TX power, manufacturer data, service data) are rebuilt from the event; HEX Structure shows them — flags, Apple iBeacon (UUID, major, minor, TX power), Eddystone (UID / URL), company ids. **BLE GATT** records have the value in `hex` (any structure can be chosen by hand).

**GSM** BCCH records carry the decoded L2 message in `hex` and `hexSchema` `gsm-l2`, cell-broadcast records (`GSM-CBS`) the 88-byte page with `gsm-cbs`. `gsm-l2` splits the message down to the bits: System Information 1 / 2 / 2bis / 2ter / 3 / 4 / 13 / 2quater — cell identity, LAI (`MCC-MNC`), LAC, control channel description (CCCH configuration, paging multiframes, T3212), cell options (DTX, radio link timeout), cell selection (hysteresis, RXLEV access minimum in dBm), RACH control parameters (max retransmissions, TX integer, access classes), the cell channel / BCCH frequency lists as ARFCN ranges (`gsm-freqs`: bitmap 0, range 1024 / 512 / 256 / 128, variable bitmap), the optional CBCH description of SI4, and the CSN.1 rest octets as a one-line summary (SI3: selection parameters, GPRS indicator; SI13: PBCCH or RAC; SI2quater: 3G neighbours). The same schema reads the CCCH messages Paging Request 1 / 2 / 3 (TMSI, IMSI / IMEI from the mobile identity) and Immediate Assignment (channel, ARFCN or MAIO / HSN, request reference, timing advance). `gsm-cbs` shows the serial number, message id, data coding scheme, page x of y and the text (GSM 7-bit, UCS-2). **GSMTAP** (UDP port 4729, the capture format of gr-gsm and Wireshark: ARFCN, signal level, frame number, channel type, then the L2 frame) opens down to the message when a `.pcap` goes through PCAP Reader → HEX Structure, also for Linux cooked (`sll`) and loopback (`null`) link types. Checked against the decoder's own parsers (`node tools/test-hexdec.mjs`). **GSM: Receive Bursts** now reads the CCCH of TS0 as well: Paging Request 1 / 2 / 3 (`GSM-PCH` records) and Immediate Assignment, Extended, Reject (`GSM-AGCH`: channel type and sub-channel, TN, TSC, ARFCN or MAIO / HSN, request reference, timing advance; the reject has the wait indication). The blocks are 6–9, 12–15, 16–19 of the 51-multiframe for a CCCH combined with SDCCH/4 and all nine for a non-combined one — the node takes it from CCCH-CONF in SI3 and until then reads only the three common blocks. The identities that paging carries (TMSI, IMSI) belong to particular subscribers, so by default the records hold only a marker (*paging identifiers* = `hash`: a hash with a random salt per session, the same subscriber gives the same marker while the receiver runs) and `hex` has those bytes zeroed; `none` leaves only the count; `show` gives them as they are (for your own network or lab). The readout shows `CCCH ok/blocks pag IA`. The IQ Generator (mode GSM) now transmits paging and assignments, so *GSM* presets show them; `node tools/test-gsm.mjs` runs the whole chain generator → receiver for both CCCH configurations and the three identifier modes. Presets *GSM: Paging, Assignments and HEX (USB SDR)* (spectrum marker on a BCCH carrier → shift → GSM: Receive Bursts → Rec Filter for paging / assignments → Table, and HEX Structure for the last control message) and *GSM: Paging, Assignments and HEX (Generator)* (the same without a radio; the IQ Generator has a *CCCH combined with SDCCH/4* switch). Since then, **GSM: Receive Bursts** also blind-decodes a dedicated channel's SDCCH/SACCH once Immediate Assignment points it there (see [GSM](radio.md#gsm)) — `GSM-SDCCH` / `GSM-SACCH` records, with `hex`/`hexSchema` `gsm-l2` for the SI5 case (reuses the SI2 schema) but a plain `hex` (no schema yet) for the MM messages (CM Service Request, Identity, Authentication, Location Updating, TMSI Reallocation); content once ciphering (A5) starts is not reached at all — the FIRE CRC that gates this decode never passes on it.

**M17** call records carry the 30-byte link setup frame in `hex` and `hexSchema` `m17-lsf` (callsigns in base-40, CAN, stream type, encryption, meta, CRC-16 checked); packet records `m17-pkt` (the protocol byte picks IPv4 for protocol 4).

**P25** records carry `hex` and `hexSchema`: TSBK blocks (`p25-tsbk`: 12 bytes with CRC-16 checked; grants, updates, status broadcasts, registration), Link Control words (`p25-lc`, from LDU1 / TDULC) and the header data unit (`p25-hdu`: message indicator, algorithm, key id, talkgroup). The old `hex` of unparsed TSBK / LC is now the whole block.

**NXDN** `call` and `msg` records carry the layer-3 message in `hex` and `hexSchema` `nxdn-l3` (calls and releases: call type, options, source and destination, cipher and key; channel assignments: timer and channel; site information; the unparsed rest as bytes). The old `hex` of an unparsed message is now the whole message.

**TETRA** `sync` and `sysinfo` records carry the PDU bits in `hex` and `hexSchema` `tetra-sync` (colour code, TN / FN / MN, MCC, MNC) and `tetra-sysinfo` (carrier, band, offset, duplex, access parameters, location area, service flags).

**DMR Signalling Builder** (Protocols): the bytes of a link-control word (9 B, `dmr-lc`) or a CSBK / PI header / data header (10 B, `dmr-csbk`, `dmr-pi`) from HEX Structure (`bin` or `text`) → Reed-Solomon RS(12,9) or CRC-16 with the burst mask, BPTC(196,96), the slot type (Golay) with the colour code and the sync word → bursts on `blk` (time slots with CACH, like DMR Data Builder) and the 33-byte burst itself on `bin` / `text`. Types: PI header, Voice LC header, Terminator LC, CSBK, MBC header, Data header. Preset *DMR: Signalling from HEX → Burst → Decoder (Loopback)* goes through Symbol Player, shaper, FM modulator and the Digital Voice Decoder and shows the decoded call in a second HEX Structure. In the structures the CRC-16 of CSBK and PI is a `calc` with `xor` (the burst mask).

**Decoders**: DMR records (LC header / end, CSBK, PI) and ADS-B demodulator records carry `hex` (the decoded bytes) and `hexSchema`; wire the decoder's `rec` to HEX Structure to see them field by field. **Wi-Fi Sniffer (ESP32)** (Sources): 802.11 frames from an ESP32 over WebSerial (Chrome / Edge) — flash [`tools/wifi-sniffer-esp32`](../tools/wifi-sniffer-esp32/wifi-sniffer-esp32.ino) (promiscuous mode, channel hopping; lines `WIFI,<channel>,<rssi>,<hex>`). Every frame is a record (type, addresses, SSID, channel, security, RSSI, `hex`), the `text` input takes the same lines without hardware. The firmware and the serial node are not tested on hardware (the line parser and the 802.11 structure are tested on sample frames). Use it on your own network or with permission; frames are not decrypted.

**Radio Bridge (ESP32-C5)** (Sources) is one node for everything the chip hears and sends: Wi-Fi (2.4 and 5 GHz; management, control and — by a separate switch — data frames; channel hopping), BLE (passive or active scan) and IEEE 802.15.4 (Zigbee, Thread, Matter-over-Thread). Flash [`tools/radio-bridge-esp32c5`](../tools/radio-bridge-esp32c5/radio-bridge-esp32c5.ino) (Arduino-ESP32 ≥ 3.3, NimBLE-Arduino ≥ 2.5; **not tested on hardware**), connect over USB (Chrome / Edge) and press *Connect*. Every frame is one record with the same names for every protocol — `proto`, `kind` (`beacon`, `probe-req`, `adv_ind`, `data`…), `src`, `dst`, `net` (BSSID or PAN), `chan`, `rssi`, plus the packet's own fields by name (`ie.ssid`, `ie.rsn.akm`, `p2p.device_info.name`, `ad.name`, `zb_cluster`…) — and `hex` / `hexSchema`, so it goes straight to *Rec Filter*, *Table*, *Rec → Entities* / *Graph* and *HEX Structure*. A filter on a device is one condition: `r.src==='aa:bb:cc:dd:ee:ff' || r.dst==='aa:bb:cc:dd:ee:ff'`. Transmit: `txbin` (bytes, e.g. from HEX Structure *build*), `txrec` (a record with `hex`, optionally `proto`) or `tx` (text: `WIFI <hex>`, `ZB <hex> csma` or bare hex for the *tx: protocol* choice) → `TX …` to the firmware. The auto-responder to Probe requests is built in: tick *auto-reply*, give the SSID and our BSSID, keep the channel fixed (a hopping radio is already elsewhere when the answer goes out); a request for another SSID is ignored, a broadcast one is answered, at most once a second per address. Any other frame is built by names in HEX Structure (`ie.ssid`, `ie.rates`, `ie.channel`; the element lengths are calculated) and sent through `txbin`. Limits: encrypted payloads stay encrypted (the CCMP / TKIP / AES header is shown), no BLE extended advertising or coded PHY, no 6 GHz; the line protocol is in the firmware header. Logic: `modules/radiobridge-kernels.js`.

**Radio Bridge: capture quality, channel levels and CSI.** The firmware keeps frames in a variable-length ring buffer (48 KB), writes one line per frame, has a bigger USB TX buffer and a deeper Wi-Fi RX queue, and cuts *data* frames to a separate length (*bytes kept per data frame*, default 96 — enough for the 802.11, LLC and IP / TCP headers; the payload is encrypted anyway), so far more frames survive; `INFO` shows `DROPPED` and `RINGFREE`, and every channel window reports its own loss. Tick *channel stats* (firmware `STAT`): the chip counts **every** frame it hears (any type, regardless of the selected classes) and sends one line per channel window (per hop dwell): frames, bytes, max / mean RSSI (−127 — nothing heard), busy % (airtime estimate from length and rate) and lost frames → output `stat` (records `chan-stat`: `id` `ch6`, `chan`, `rssi_max`, `rssi_avg`, `busy`, `fps`, `frames`, `drop`). Tick *CSI* (firmware `CSI ON <ms>`): output `csi` (records `csi`: `src`, `chan`, `rssi`, `sc`, and the lists `csi` — amplitude and `csi_ph` — phase per subcarrier, comma separated). Wire `stat` to a Table with key `id` (the latest window per channel) and its `all` to **Table Chart**; `csi` goes to a plain Table (history) and to a chart (lines or *heat*). Preset *Radio: Wi-Fi channel level · occupancy · CSI*. **Not tested on hardware**: the CSI config fields (`acquire_csi_legacy`, `acquire_csi_ht20`) compile on the C5 SDK, but the CSI itself was not seen on the air; airtime uses the rx_ctrl `rate` plus the bb format / MCS when the SDK has those fields (else an MCS 7 guess for non-legacy frames), so treat busy % as an estimate. If the sketch does not compile, set `WITH_CSI 0`.

**HEX Field Finder** (Data) looks for fields in packets of an unknown format: records with a hex field (decoders, Table, PCAP Reader), `bin` or hex lines pile up; packets of one length (or of one kind and length) are compared byte by byte. It reports candidates with a score 0…1: Unix time (a time equal to the capture time scores highest), latitude / longitude (integers divided by 10^k, 60, 360, 3600…, or 360/2^n, little- or big-endian, signed or not — the values must cluster in a narrow window and change smoothly from packet to packet; a range check alone is not enough, random bytes pass it), float32 / float64 degrees, counters (+1 or +k), identifiers (few distinct values), ASCII text, BCD, a CRC or sum of the tail over the preceding bytes, constants and random runs. Packets of one length are split by the layout of their zero bytes (padding, empty fields). If nearly all changing bytes are random and no checksum is found, the verdict is *looks random: encrypted, compressed or noise*. The `rec` output carries the candidates, `text` a draft structure (JSON) for HEX Structure (advanced → own structure), *Copy schema JSON* puts it on the clipboard. From the command line: `node tools/hex-scan.mjs capture.csv [--col hex|raw|data] [--group-by kind,rate] [--schema]`. The heuristics find what is there; they say nothing about what a field means — that stays with a human. **Except with a reference:** if the quantity the packets carry is known — a thermometer next to the sensor, a voltmeter, a signal generator — wire it to the **`ref`** input (or name a number field of the record in *reference quantity*; *reference name* and *unit* label the result) and every packet is stored with the reference value it arrived with. The finder then correlates the reference with every byte column (1–4 bytes, big / little endian, signed or not), with every window of 3–16 **bits** at any bit offset (most sensors pack 10- and 12-bit values with flags) and with BCD numbers of 2–4 digits, and prints the best non-overlapping ones as `quantity`: `temperature ≈ 0.1·x − 40 °C (r=0.9999, rmse 0.03, 150 pkts, 12 bits from bit 32)`. The scale snaps to a round number (0.1, 0.01, 1/16, 5…) when it is within 2 %, the offset to a multiple of it when it is within the error. Counters are not taken for a quantity even when the reference is a ramp; a constant reference is reported as such (vary it while recording); windows that tie are resolved toward the byte boundary, then toward the narrower window, and a window that starts in the middle of a byte grows over constant leading bits of that byte. The draft structure then has the field with `scale`, `bias` (new in HEX Structure: the shown value is `v·scale + bias`), `prec` and `unit`; a field that is not byte-aligned becomes a `bits` field, the rest of the packet stays bytes and bits. From the command line: `--ref temp --unit "°C"` (a CSV column). Preset: *Hex: Reverse a Sensor — Find the Temperature Field by a Reference*. It needs a reference that actually changes (tens of packets over a few °C or volts), and a correlation is not a proof: a reference that drifts together with an unrelated slow field can fool it, so look at `r`, `rmse` and the number of packets. Logic: `modules/hex-scan-kernels.js`, `node tools/test-hexscan.mjs` (synthetic tracks with a counter, time, latitude / longitude, checksum; angles as 16 bits of a circle; random and half-encrypted packets must not produce coordinates).

Presets *Hex: Parse a Packet (Ethernet / IPv4 / UDP)*, *Hex: PCAP File → Packets → HEX Structure*, *Hex: Table Rows → Packets → Table*, *Wi-Fi: ESP32 Sniffer → Table and HEX Structure*. Logic: `modules/hex-kernels.js`, structures `modules/hex-formats.js`, `node tools/test-hex.mjs` (CRC check values, the Wikipedia IPv4 header, the classic ADS-B frame with CRC-24, build / parse round trips, endianness and bit order, truncated packets, structure checks).

## Protocol registry and Protocol Codec

`modules/protoreg-kernels.js` keeps one record per protocol: which kernel functions parse it, which build it, which only generate a test signal. A protocol with a codec adapter is **checked**: `protoRoundtrip(id)` builds the sample fields to bytes, parses them back and compares (`node tools/test-protoreg.mjs`).

**Protocol Codec** (`protoCodec`, cat Protocols) is the node for it: pick a protocol and a mode.

- *loopback* — fields → hex → fields; shows ✓ or the fields that differ.
- *encode* / *decode* — fields (JSON, from the parameter or the `fields` pin; empty — the protocol's sample) ⇄ hex (the `hex` pin).
- *list* — the whole registry as records on `rec` (feed a Table): `status` is `pair` (round trip checked), `both` (functions on both sides, no check yet), `gen` (decoder + test generator only), `dec` / `enc` (one side only).

Adapters exist for ADS-B (DF17 ident, position, velocity), RDS (PS, RadioText, AF, clock), Remote ID, NTP, TFTP, DNS, BLE GATT values, Syslog, SMS PDU, DCF77 and LZHUF. Test signals with emergency / service codes are never meant for the air. Preset: *Protocol Registry: Encode → Decode Loopback and Mirror-Pair List*.
